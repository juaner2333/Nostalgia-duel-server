## Context

变更动机参见 `proposal.md`，行为契约参见 `specs/ygopro-only-server/spec.md`。

当前进程从同一个入口启动两套决斗服务：EDOPro TCP/WebSocket 服务器和 YGOPro TCP/WebSocket 服务器。两者尚未完全分离，YGOPro 与共享代码仍会导入 EDOPro 所有的消息解析、连接分发、房间状态行为、客户端类型、禁限卡表类型和仓库。共享统计订阅者又是通过构造 EDOPro `HostServer` 的副作用完成注册，因此如果不先迁移注册逻辑便删除该服务器，YGOPro 统计持久化会在没有明显错误的情况下停止工作。

EDOPro 的 `HostServer` 与 `WSHostServer` 实际位于 `src/socket-server/`，而不是 `src/edopro/`。物理删除范围必须按运行时职责和启动引用确定，不能只按目录名判断。

部署流程还会构建原生 EDOPro CoreIntegrator、创建并热重载 `evolution_cards.db`、拉取完整的 EDOPro 卡片与脚本仓库、发布 `edopro` 资源树并暴露 EDOPro 端口。资源更新器每次刷新都会重新发布整棵资源树。当前本地测量结果显示：一份组装后的 EDOPro 资源树约为 107 MB，两个最大的 EDOPro 源仓库检出目录共约 129 MB，生成的 SQLite 数据库约 11 MB，原生核心目录约 4.2 MB，两个主要的 EDOPro 专用原生 Node 包约占 20 MB。

实现必须遵循现有 DDD/六边形架构边界，测试必须与源码同目录，不得为了本次移除工作引入新的第三方包，并保证每个中间变更均可构建。

## Goals / Non-Goals

**目标：**

- 在保留受支持 YGOPro 行为的前提下，使应用依赖图和生产产物仅包含 YGOPro。
- 恢复向内依赖：共享领域层与应用层代码不得导入任何客户端模块。
- 消除 EDOPro 启动工作、端口、定时器、原生二进制、SQLite 数据库生成、资源刷新工作及遗留部署数据。
- 让统计与事件订阅独立于任何 Socket 服务器构造函数。
- 在 YGOPro 资源和决斗冒烟测试通过前，保留安全的部署回滚边界。
- 测量变更前后的镜像、磁盘、启动时间和资源刷新成本。

**非目标：**

- 重新设计 YGOPro 协议、房间状态机、录像格式、匹配或 WindBot 行为。
- 借本次删除工作重命名所有残留的 `Mercury` 或 `Evolution` 概念。
- 将 Postgres、Valkey、排行、认证或资源更新器改为可选；这些属于独立的成本优化变更。
- 仅因上游项目与 Project Ignis 有关而裁剪有效的 YGOPro 资源。
- 替换当前资源清单框架，或新增资源管理依赖。

## Decisions

### 1. 先解除依赖，再删除文件

本次变更会先在 EDOPro 模块仍存在时，使 YGOPro 与共享代码无需导入 `src/edopro` 即可通过编译和测试，之后才删除入口和实体文件。

依赖归属调整如下：

| 现有依赖 | 目标归属 |
| --- | --- |
| YGOPro 服务器使用的 EDOPro `MessageEmitter` | YGOPro 连接/消息分发 |
| `PlayerInfoMessage` | YGOPro 线协议解析器，加协议无关的认证输入结构 |
| EDOPro `RoomState` 基类 | 仅包含 YGOPro 版本、聊天、表情和通知行为的 YGOPro 房间状态基类 |
| 共享房间代码中的 EDOPro `Client` 引用 | 现有协议无关的 `YgoClient` |
| 校验器中的 `EdoproBanList` | 视场景使用共享 `BanList` 契约或具体的 `YGOProBanList` |
| 混合实现的 `RoomFinder` 和 `DisconnectHandler` | YGOPro 应用服务 |
| 导入 YGOPro `HostInfo` 的共享消息仓库 | YGOPro 房间/消息端口 |
| 认证逻辑返回 EDOPro 线协议缓冲区 | 在 YGOPro 边界序列化的领域认证结果 |

该方案优于将 EDOPro 文件整体移动到 `shared`，因为其中若干文件混合了协议行为，迁移目录只会用中性名称掩盖原有架构耦合。该方案也优于功能开关，因为部署环境没有 EDOPro 使用方，保留开关仍会保留维护与打包成本。

### 2. 通过独立启动流程注册统计订阅

统计订阅者将由显式的应用启动流程注册一次：在所需持久化设施就绪之后、决斗服务器接收流量之前执行。注册不再是构造 Socket 服务器时产生的副作用。

首次重构保留当前启用语义。未来若要在关闭排行时同时关闭基于 Postgres 的订阅者，应放入独立的持久化成本变更。测试需要证明一条 YGOPro 游戏结束事件会恰好一次送达每个已配置订阅者。

### 3. 将 YGOPro 禁限卡表作为唯一标识来源

卡组校验、房间展示、录像元数据和游戏结束事件将统一使用 `YGOProBanList` 的名称与哈希。移除 EDOPro 仓库查询及 `_edoBanListHash` 快照。

本地安装的 YGOPro 禁限卡表编码器对普通 0–2 限制条目使用相同的旧版滚动公式；点数制/Genesys 扩展应使用 YGOPro 库自身的哈希，而不是独立解析得到的 EDOPro 近似值。通过有代表性的普通卡表与点数制卡表测试锁定该行为。

不采用“仅为兼容哈希而保留 EDOPro 仓库”的方案，因为这会保留本次变更计划消除的资源与领域耦合。

### 4. 保留中性 HTTP 路由，但仅提供 YGOPro 数据

继续保留房间列表、禁限卡表检查、数据库检查、卡片搜索、资源版本和管理消息等中性路由。只要语义仍成立，就保留现有路由和查询结构，但引擎参数只接受 `ygopro`，混合响应结构不再包含 `edopro` 分支。

移除 EDOPro 专用 HTTP 房间创建行为。旧版通用房间列表端点可以作为 YGOPro 专用兼容视图，与较新的 YGOPro 房间列表端点同时保留。管理消息改用 YGOPro 序列化器。

不保留空的 `edopro` 数组，因为这会错误宣称系统仍支持该引擎，并延续双引擎客户端契约。

### 5. 不发布任何 EDOPro 专用资源源或目标

资源清单中不再包含仅供 EDOPro 使用的卡片数据库、脚本、禁限卡表树、资源源、`edopro/*` 组装目标或运行时路径。资源源的归属按其全部消费者判断，不按 ID 是否包含 `edopro` 判断。对公共清单和可选私有清单中每个供给 `edopro/*` 目标的资源源，都必须列出全部组装规则，并逐源记录“删除、保留或重命名”的结论。

当前公共清单的结论如下：

| 资源源 | 当前消费者 | 处理结论 |
| --- | --- | --- |
| `edopro-cdbs` | 仅 `edopro/databases` | 删除资源源与目标 |
| `edopro-scripts` | 仅 `edopro/scripts` | 删除资源源与目标 |
| `edopro-lflists` | `edopro/lflists`，以及 YGOPro 的 world、speed、rush、goat、ocg 赛制 | 删除 EDOPro 目标；将资源源 ID 重命名为中性的 `project-ignis-lflists`，保留全部 YGOPro 文件映射 |
| `evolution-lflists` | `edopro/evolution-lflists`，以及 YGOPro 的 MD、Tengu 赛制 | 删除 EDOPro 目标；保留资源源及 MD、Tengu 文件映射 |

若私有清单覆盖或新增上述资源源/目标，也必须使用同一消费者归属规则重新分类。资源断言应检查有效组装图中是否仍有 `edopro/*` 目标或仅供 EDOPro 使用的资源源，不能只对资源源 ID 做字符串匹配。

保留 YGOPro 资源树下的 YGOPro WASM 核心。根目录中的原生 `core/` 与该 WASM 运行时无关，应予删除。

不采用“为已无消费者的 EDOPro 目标继续复制完整上游仓库”方案，因为它无法达成磁盘占用、刷新 I/O 和维护成本目标。对于仍供给 YGOPro 赛制的共享源，本次优先保证行为不回归；后续只有在来源、刷新和完整性验证等价时，才可进一步收缩为文件级资源源。

### 6. 将安全发布与破坏性部署清理解耦

干净构建自然不会包含已删除资源，但升级安装可能残留仓库缓存、旧发布版本、生成的 SQLite 文件、镜像、数据卷或外部端口配置。因此，清理应作为显式部署步骤，在新资源版本和应用镜像通过健康检查与 YGOPro 决斗冒烟测试后执行。

仓库与发布版本的删除目标必须解析为明确的 EDOPro 路径或旧发布 ID。清理操作不得将工作区根目录、资源根目录或未解析的环境变量作为递归删除目标。

本次变更不引入通用的仓库自动垃圾回收，因为这会扩大更新器的破坏性行为范围。更新器只需停止创建 EDOPro 数据，既有数据由升级运行手册一次性处理。

### 7. 仅在确认无引用后移除构建依赖

移除原生 CoreIntegrator Docker 阶段、原生文件复制步骤和 EDOPro 辅助脚本。EDOPro 删除产生的直接候选包包括 `lzma-native`、`shuffle-array`、`better-sqlite3` 及其 EDOPro 专用类型包；全仓库引用审计还发现既存无导入的直接依赖 `cheerio`、`simple-git`、`load-json-file` 和 `array-shuffle`。删除前重新确认生产代码、脚本和测试均无引用，再通过 npm 重新生成锁文件并检查最终依赖树。

最终镜像当前安装 `liblua5.3-dev`、`libsqlite3-dev` 和 `libevent-dev`。只有在依赖树检查与干净镜像运行验证均证明 WindBot、YGOPro WASM Worker 及其运行时不依赖对应库后，才能移除这些系统包；无法证明无依赖的库继续保留。

保留 `better-lock`、YGOPro 编码器包、`koishipro-core.js`、`yuzuthread` 和 YGOPro WASM 核心。若通用工具或基准脚本仍有 YGOPro 使用方，则重命名或继续保留，不得仅因历史命名而删除。

### 8. 同时设置行为与产物门禁，不只依赖 TypeScript 编译

实现遵循仓库的测试优先循环：先新增或更新一个会失败的特征测试/契约测试，再进行最小化生产代码变更，然后先重跑聚焦测试，最后执行更广泛验证。

完成门禁包括：

- 不存在解析到 `src/edopro` 的导入或路径别名；
- `src/shared` 不导入任何客户端专用模块；
- 生效的资源清单中不存在 `edopro/*` 目标或仅供 EDOPro 使用的资源源，且所有保留的 YGOPro 赛制资源仍可解析；
- 不存在 EDOPro 监听器或对外发布端口；
- 干净生产镜像清单中不包含原生 CoreIntegrator、EDOPro SQLite 或 EDOPro 资源；
- 通过当前 MDPro3 固定线协议样本、真实 TCP 接入、YGOPro WebSocket、房间生命周期、重连、禁限卡表、录像、API、统计和资源测试；
- 通过完整的代码检查、测试、构建、Bats 资源测试、容器启动及完整 YGOPro 决斗冒烟测试；
- `.github/workflows/pipeline.yaml` 对应的 CI 流水线全部通过；
- 取得镜像体积、资源/仓库磁盘占用、启动时间、空闲内存和单次刷新周期的变更前后数据。

### 9. 以 MDPro3 固定线协议样本作为 WSL 回归边界

当前 MDPro3 在 TCP 连接建立后依次调用 `CtosMessage_ExternalAddress`、`CtosMessage_PlayerInfo` 和 `CtosMessage_JoinGame`。每个帧使用二字节小端长度前缀，长度包含一字节命令；当前命令分别为 `0x17`、`0x10`、`0x12`，客户端版本为 `0x1362`。`PlayerInfo` 写入 20 个 UTF-16LE 字符槽，`JoinGame` 在版本后写入两个 `0xCC` 字节、32 位保留/游戏 ID 字段和 20 个 UTF-16LE 字符槽的口令。

服务端测试中提交一份由上述客户端实现生成并人工核对的固定十六进制样本及其预期字段。该样本是兼容契约，不在测试运行时引用客户端仓库或重新实现一套仅用于生成期望值的编码器。客户端主动调整线协议时，必须显式更新样本、规范和预期解析结果。

回归分为两层：

1. **WSL 阻断层**：使用 Node.js/Jest、临时 loopback 端口和模拟客户端覆盖固定样本解析、长度前缀拆分、负载拆分、多帧粘包、非法/截断帧、版本拒绝、错误口令、重复玩家、完整加入流程、房间生命周期、WebSocket 与 HTTP 契约。该层不启动 Unity，也不依赖 Windows 图形环境，可以作为每次重构提交的稳定门禁。
2. **Windows 发布层**：候选版本通过 WSL 层后，从 Windows 启动真实 MDPro3 构建并连接运行在 WSL 中的服务端，完成进入房间、卡组提交、双方准备、开局和结束一场最小决斗，同时保存双端日志。该层验证 Unity 运行时、Windows/WSL 网络和真实资源装载，但不替代可重复的 WSL 协议测试。

当前 MDPro3 在线流程使用 TCP，未发送服务端 WebSocket 重连命令。因此 WebSocket 和令牌重连继续作为独立的 YGOPro 服务端兼容回归，不得将其误记为当前 MDPro3 客户端覆盖。

## Risks / Trade-offs

- [迁移共享房间状态行为可能导致 YGOPro 聊天、表情、版本拒绝或通知回归] -> 提取前增加 YGOPro 特征测试，只保留 YGOPro 状态实际使用的行为。
- [移除 `HostServer` 可能无声地禁用统计] -> 在移除任一 EDOPro 服务器前，先落地并验证独立统计启动流程。
- [更改禁限卡表哈希可能割裂历史统计与新统计] -> 测试有代表性的卡表，记录新事件使用 YGOPro 哈希，且不重写历史数据行。
- [HTTP 调用方可能依赖 `edopro` 字段] -> 将响应结构变化视为破坏性变更并记录；尽量保留中性路由路径，同时在同一版本更新检查页面与测试。
- [双用途 LFList 资源源可能因曾供给 EDOPro 目标而被连带删除] -> 按全部消费者建立资源源矩阵；明确保留 `evolution-lflists` 的 MD/Tengu 映射，以及重命名后的 Project Ignis 源所供给的 world、speed、rush、goat、ocg 映射，并为每个保留赛制通过建房与卡组校验冒烟测试。
- [删除代码后旧资源仍可能占用磁盘] -> 加入明确的部署后盘点与清理，不能仅凭源码树检查就宣告成本目标达成。
- [删除 `liblua5.3-dev`、`libsqlite3-dev` 或 `libevent-dev` 可能暴露未记录的 WindBot/YGOPro 运行时依赖] -> 删除前检查依赖树，并使用干净 Docker 镜像完成 WindBot 与 YGOPro WASM 冒烟测试；无法证明无依赖的库继续保留。
- [测试内重新拼装握手期望值可能与客户端同步漂移并产生假通过] -> 提交独立的固定十六进制样本和已知解析结果，客户端协议变化时要求显式评审样本差异，并由真实 Windows 客户端冒烟测试兜底。
- [WSL 模拟客户端通过但 Windows/Unity 或跨宿主机网络仍失败] -> 将真实 MDPro3 到 WSL 服务端的最小决斗作为候选版本发布门禁，并保留双端日志。
- [大规模删除会增加评审与回滚难度] -> 将依赖解除、运行时切换、实体删除和部署清理保持为有序且可独立验证的任务组。

## Migration Plan

1. 记录当前镜像体积、资源/仓库占用、生成数据库大小、启动时间、空闲内存、活动端口和资源刷新耗时。
2. 在两套协议实现仍可编译时，落地 YGOPro 特征测试、显式统计启动流程以及所有依赖边界迁移。
3. 将启动、持久化、HTTP、禁限卡表重载、资源清单和部署配置切换为仅支持 YGOPro。
4. 删除 EDOPro 源码、原生核心、SQLite 路径、测试、别名、包、脚本、文档和构建阶段；从干净检出的代码与干净 Docker 构建进行验证。
5. 发布新镜像和 YGOPro 专用资源版本，同时保留上一版镜像与资源版本作为回滚资产。
6. 验证健康状态、配置端口、资源清单、管理 API、统计持久化，以及一场包含录像产出的完整怀旧赛制 YGOPro 决斗。
7. 关闭 EDOPro 入口和健康检查，并移除已明确识别的 EDOPro 仓库缓存、生成的 SQLite 文件、旧发布版本、镜像和数据卷。
8. 记录变更后的成本数据，并确认定时刷新不会重新创建 EDOPro 数据。

在第 7 步前回滚时，使用上一版镜像，将 `resources/current` 重新指向保留的上一版资源，并恢复原入口配置。执行破坏性清理后，回滚需要重新构建并部署上一版本及其资源，因此清理被刻意安排在最后。
