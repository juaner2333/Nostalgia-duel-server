## Context

动机与对外行为见 [proposal.md](./proposal.md) 和 [半年赛季 spec](./specs/nostalgia-half-year-ranked-seasons/spec.md)。当前排位在 Match 结束时按北京时间将 `YYYYMM` 写入 `matches.season`，并按 `(user_id, format_id, season)` 累加 `player_stats` 的积分、胜场和败场；各场积分变化是可加的。天梯 API 的赛季查询只取单月，页面默认当前月，进房提示也查单月。总榜已跨所有月份求和。

## Goals / Non-Goals

**Goals:**

- 在不迁移或删除历史月度事实的前提下，让页面、API 与进房提示使用同一半年赛季结果。
- 让 1 月 1 日和 7 月 1 日边界准确切换，并保持 1103、1109 及总榜的既有隔离与排序。

**Non-Goals:**

- 不修改逐场积分公式、MATCH 结算事务、录像或卡组快照。
- 不把使用率的每日批处理引入实时天梯查询；使用率由配套变更独立实现。

## Decisions

### 1. 半年赛季为查询视图，月度事实继续保存

新增共享的北京时间半年标识与边界计算：H1 对应 `YYYY01`–`YYYY06`，H2 对应 `YYYY07`–`YYYY12`，对已结算 Match 的月度 `season` 做包含端点的整数范围查询。半年榜按 `(format_id, user_id)` 将范围内的 `player_stats.points/wins/losses` 求和，再按现有 `points DESC, wins DESC, username ASC` 排名、搜索和分页。跨期总榜查询不变。这样历史 2026H1 和 2026H2 可从已有月度记录直接重建，不需要为同一积分维护第二份可变汇总，也不需要数据迁移。

备选是把 `matches.season` 和 `player_stats.season` 全部改写为半年编码，需要迁移已应用事实、处理服务新旧版本并行写入，还会影响其他依赖月度字段的查询；没有必要。另一个备选是每次从 `matches` 逐场求和，低数据量虽可行，却绕过当前可靠的 `player_stats` 汇总路径。

### 2. API、页面和进房提示共用一个半年口径

`GetLeaderboard` 严格解析 `YYYYH1|YYYYH2` 并传递对应的月度整数范围给仓库。仓库复用现有总榜的分组、排序和胜率计算方式，只增加有界 `season BETWEEN startMonth AND endMonth` 条件；个人当前半年战绩从同一排行结果取得排名，零场次返回零与未上榜。进房提示依据北京时间当前半年调用该查询。页面将 `type=month` 输入替换为年份与 H1/H2 选择，默认当前半年，历史选择和总榜继续复用现有搜索、分页、打码与请求失败处理；切换半年重置页码。

备选是分别在页面和进房逻辑中计算半年边界，容易在时区或 7 月 1 日发生分歧。继续接受 `YYYY-MM` 并暗中映射到半年会让旧链接看似月榜却返回半年数据，因此 API 对旧参数返回 400。

### 3. 与使用率周期只共享边界定义

天梯在每场 Match 结算后实时累加月度事实，半年榜随之更新；使用率每日批处理只统计已结束的北京时间自然日。两个页面均采用 1 月 1 日与 7 月 1 日边界，但更新时间不同，文案必须分别说明。配套使用率变更的聚合表不参与天梯积分查询。

## Risks / Trade-offs

- `[旧客户端仍请求月榜参数]` → 将 API 变化标记为破坏性，更新页面与文档；旧参数明确返回 400，不提供含义模糊的数据。
- `[半年范围聚合比单月查询更慢]` → 复用现有 `player_stats(format_id, season, ...)` 索引，在接近生产数据量的样本上核对执行计划与响应时间。
- `[未归档的旧变更仍描述月赛季]` → 本变更明确记录新行为；归档或同步规格时先处理旧变更，再以本变更覆盖月赛季条款，避免主 spec 被旧内容覆盖。

## Migration Plan

1. 用现有月度记录核对两个环境的 2026H1/H2 聚合、总榜及 6 月 30 日/7 月 1 日边界。
2. 发布 API、页面和进房提示的同一版本；无需数据库迁移或清除历史月度行。
3. 发布后核对当前半年榜、历史半年榜、总榜和进房提示的一致性。回滚应用版本即可恢复旧月榜，原始月度事实保持完整。
