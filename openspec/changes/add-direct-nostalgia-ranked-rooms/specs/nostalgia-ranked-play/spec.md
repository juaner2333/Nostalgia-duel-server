## Purpose

定义可独立启停的低在线人数怀旧服直接排位能力，使已认证玩家可按固定格式或裸 `TT` 默认 1109 入口进入可等待的排位房、断线后恢复原席位，进房时获知当前月赛季战绩，并让比赛结果从 0 分开始按格式和北京时间自然月独立计分、在整场终结后保存每一小局的排位录像，同时提供月赛季榜与跨月总榜并保持普通数字房间的匿名非排位行为。

## ADDED Requirements

### Requirement: 排位能力由单一开关控制

服务器必须（SHALL）使用 `RANK_ENABLED` 作为排位准入、账号认证、比赛持久化和排行榜的统一能力开关。关闭时服务器不得（SHALL NOT）连接或要求 PostgreSQL，必须（MUST）继续提供普通数字房；开启时 PostgreSQL 连接成功且数据库不存在待执行 Migration 必须（MUST）是服务接受客户端连接的前置条件。Migration 必须（MUST）由运维人员在启动或升级服务前显式执行，应用启动不得（SHALL NOT）自动修改数据库模式。关闭时不得（SHALL NOT）静默启用任何部分排位能力。

#### Scenario: 极简模式不部署 PostgreSQL

- **WHEN** 使用原有 `docker-compose.cloud.yaml` 启动服务
- **THEN** 编排只启动关闭排位的决斗服务，不启动 PostgreSQL 或 Valkey，并且普通 `1103#数字` 与 `1109#数字` 房间继续可用

#### Scenario: 关闭排位后访问 TT

- **WHEN** `RANK_ENABLED=false` 且玩家使用裸 `TT` 或任一已启用格式的 `format#TT` 加入
- **THEN** 服务器拒绝该排位加入，不连接 PostgreSQL，也不创建账号、排位房或账号占用记录

#### Scenario: 关闭排位后访问排行榜 API

- **WHEN** `RANK_ENABLED=false` 且用户访问排位排行榜 API
- **THEN** 服务器返回明确的排位功能不可用响应，不尝试查询 PostgreSQL，也不回退到其他统计数据

#### Scenario: 运维人员完成迁移后启动排位模式

- **WHEN** 运维人员先启动 `docker-compose.cloud.ranked.yaml` 中的 PostgreSQL，使用应用镜像显式执行 `npm run migration:run:prod` 且全部待执行 Migration 成功，再启动排位服务
- **THEN** 编排以 `RANK_ENABLED=true` 启动决斗服务并提供 TT 排位和排行榜，不要求 Valkey

#### Scenario: 排位数据库或迁移不可用

- **WHEN** `RANK_ENABLED=true` 但 PostgreSQL 无法连接、健康检查失败或数据库仍存在待执行 Migration
- **THEN** 决斗服务不得（SHALL NOT）开始接受客户端连接，且不得静默降级为关闭排位的服务

#### Scenario: 重建排位容器保留数据

- **WHEN** 运维人员使用同一已配置宿主机数据目录重新创建 `docker-compose.cloud.ranked.yaml` 中的 PostgreSQL 和决斗服务容器
- **THEN** 已提交的账号、比赛、录像和排行榜数据继续存在；如镜像包含新的 Migration，运维人员只需在启动新服务前显式应用尚未记录的 Migration

### Requirement: 使用 TT 入口直接加入排位房

服务器必须（SHALL）把已启用格式的精确 `format#TT` 标识解释为对应格式的排位入口，并把不带格式和 `#` 的精确裸标识 `TT` 规范化为 `1109#TT` 后执行完全相同的准入、合房和重连逻辑。当前显式入口必须（SHALL）为 `1103#TT` 和 `1109#TT`，默认格式固定为 1109；`TT` 必须（SHALL）区分大小写且是完整输入，不得通过模糊匹配接受其他写法。

#### Scenario: 裸 TT 默认进入 1109 排位

- **WHEN** 尚未占用排位房的已认证玩家只输入精确的 `TT`，且当前没有可接纳该玩家的 1109 排位等待房
- **THEN** 服务器按 `1109#TT` 创建固定 1109 环境的排位房并将玩家放入玩家席位，不要求玩家补充环境参数

#### Scenario: 裸 TT 补入已有 1109 等待房

- **WHEN** 尚未占用排位房的已认证玩家只输入精确的 `TT`，且存在可接纳该玩家的 1109 排位等待房
- **THEN** 服务器按与显式 `1109#TT` 相同的顺序补入该房间，不查找或创建 1103 排位房

#### Scenario: 已占用 1103 的账号使用裸 TT 重连

- **WHEN** 账号已经占用 1103 排位房，又使用裸 `TT` 建立满足重连条件的连接
- **THEN** 服务器先遵循账号唯一占用规则恢复其原 1103 席位，不为该账号创建或占用 1109 排位房

#### Scenario: 第一名 1103 玩家立即进入等待房

- **WHEN** 已认证玩家使用 `1103#TT` 加入，且当前没有可接纳该玩家的 1103 排位等待房
- **THEN** 服务器立即创建固定 1103 环境的排位房、将该玩家放入玩家席位并让房间保持等待状态，不等待第二名玩家后才建房

#### Scenario: 第二名同格式玩家补入等待房

- **WHEN** 已认证玩家使用 `1103#TT` 加入，且存在至少一个仍有玩家空位的 1103 排位等待房
- **THEN** 服务器将该玩家加入最早创建的合格等待房，而不是创建新房

#### Scenario: 已有房间不可补位时创建新房

- **WHEN** 已认证玩家使用 `1103#TT` 加入，但现有 1103 排位房均已满员、已经开战或正在终结
- **THEN** 服务器创建新的 1103 排位等待房并将该玩家加入

#### Scenario: 两种格式保持隔离

- **WHEN** 1103 排位等待房存在，而玩家使用 `1109#TT` 加入
- **THEN** 服务器不得（SHALL NOT）将该玩家放入 1103 房间，并按 1109 格式查找或创建排位等待房

#### Scenario: 后续启用格式复用 TT 行为

- **WHEN** 应用通过固定格式注册表显式启用一个新格式，且玩家使用 `<新格式>#TT` 加入
- **THEN** 服务器使用与 1103、1109 相同的直接合房规则，并绑定该新格式自己的固定资源与计分维度；裸 `TT` 的默认格式仍保持 1109，除非未来通过独立变更修改该契约

### Requirement: TT 入口不使用排队票据

直接排位流程不得（SHALL NOT）要求玩家先取得排队票据、轮询匹配状态或等待定时任务配对，也不得（SHALL NOT）在无人时以 WindBot 替代真人对手。

#### Scenario: 单名玩家持续等待真人

- **WHEN** 一名玩家进入排位等待房且暂时没有第二名真人玩家
- **THEN** 该房间继续允许玩家停留和准备，服务器不创建排队票据、不自动加入 WindBot，也不因缺少匹配轮询而移除该玩家

#### Scenario: 旧排队接口不可用

- **WHEN** 客户端请求旧的排队创建、状态轮询或取消接口
- **THEN** 服务器报告这些接口不可用，且不创建票据、排位房或 WindBot

### Requirement: 排位玩家使用昵称和四位 PIN 认证

每个申请排位玩家席位的 YGOPro `PlayerInfo` 必须（MUST）使用 `昵称$PIN`，其中昵称非空且不得包含 `$`，PIN 必须恰好由 4 个十进制数字组成，完整值必须适配 `PlayerInfo` 的 20 个 UTF-16LE 字符槽。服务器不得（SHALL NOT）把 PIN 写入日志、排行榜或比赛展示数据。

#### Scenario: 已有账号使用正确 PIN

- **WHEN** 玩家以 `昵称$1234` 进入裸 `TT` 或显式 `format#TT`，该昵称账号已存在、未封禁且保存的密码与 `1234` 匹配
- **THEN** 服务器以该账号身份继续排位准入，并仅以不含 `$1234` 的昵称作为显示名

#### Scenario: 不存在的昵称自动注册

- **WHEN** 玩家以有效的 `昵称$1234` 进入裸 `TT` 或显式 `format#TT`，且数据库中不存在完全相同昵称的账号
- **THEN** 服务器以该昵称作为唯一键创建 PIN 账号、安全保存密码摘要，并在同一次加入流程中以新账号身份继续准入

#### Scenario: 同名并发注册保持唯一

- **WHEN** 两个连接并发尝试以相同昵称创建 PIN 账号
- **THEN** 数据库中至多产生一个该昵称账号，只有提供最终账号有效 PIN 的连接可以取得该账号身份

#### Scenario: 已有账号使用错误 PIN

- **WHEN** 玩家为已存在昵称提供错误 PIN
- **THEN** 服务器拒绝排位加入，不创建账号、不创建或加入排位房，也不暴露账号是否存在之外的密码信息

#### Scenario: PIN 格式无效

- **WHEN** `PlayerInfo` 缺少 `$`、昵称为空、包含多个 `$`，或者 `$` 后不是恰好 4 位数字
- **THEN** 服务器拒绝排位加入且不产生账号、房间或当前房间占用记录

#### Scenario: 封禁账号尝试加入

- **WHEN** PIN 正确但对应账号处于有效封禁状态
- **THEN** 服务器拒绝排位加入且不创建或加入排位房

### Requirement: 成功进入排位席位后私发当前赛季战绩

玩家每次通过裸 `TT` 或显式 `format#TT` 成功进入或重连排位玩家席位后，服务器必须（MUST）向该连接恰好发送一条私有系统消息，展示该房间格式与北京时间当前自然月赛季的积分、胜场、败场、胜率和排名。胜率必须（MUST）按 MATCH 胜场除以胜场与败场之和计算并显示为百分比；没有已结算 MATCH 时按 0% 显示。排名必须（MUST）使用对应格式当前月榜的相同稳定排序，并且消息不得（SHALL NOT）广播给其他玩家或观战者。

#### Scenario: 有当前赛季记录的玩家进入排位

- **WHEN** 玩家成功进入 1103 排位席位，且其北京时间当前月的 1103 统计为 106 分、3 胜、1 负并位列月榜第 5 名
- **THEN** 服务器只向该连接发送一条包含“1103、当前 `YYYY-MM`、106 分、3 胜、1 负、75%、第 5 名”的系统消息

#### Scenario: 当月尚未完成比赛的玩家进入排位

- **WHEN** 新账号或当前格式当前月尚无 `player_stats` 记录的账号成功进入排位席位
- **THEN** 服务器不提前创建统计行，只向该连接显示“0 分、0 胜、0 负、0%、未上榜”

#### Scenario: 玩家成功重连原排位席位

- **WHEN** 玩家在重连窗口内通过裸 `TT` 或对应格式的 `format#TT` 成功恢复原席位
- **THEN** 服务器基于原房间格式重新查询并私发当前月赛季战绩，且本次连接只收到一条该提示

#### Scenario: 观战者或准入失败连接

- **WHEN** 连接只取得观战席位，或因 PIN、封禁、格式、房间状态等原因未成功进入排位玩家席位
- **THEN** 服务器不得（SHALL NOT）向该连接发送排位赛季战绩消息，也不得泄露其他账号的统计

### Requirement: 同一账号同时只能占用一个排位房

服务器必须（SHALL）从账号被接纳为排位玩家起，到等待退出或房间统一终结为止，维护该账号唯一的活动排位房归属。该唯一性必须（MUST）跨越所有格式；普通观战连接不得（SHALL NOT）被登记为排位玩家占用。

#### Scenario: 账号重复进入相同格式

- **WHEN** 已占用排位房的账号再次使用相同格式的 `#TT` 入口连接
- **THEN** 服务器优先把有效的新连接恢复到原玩家席位，不创建新房、不占用第二个席位

#### Scenario: 账号尝试跨格式重复进入

- **WHEN** 账号已占用 1103 排位房，又使用 `1109#TT` 加入
- **THEN** 服务器恢复或指引其返回原 1103 排位房，不得（SHALL NOT）让该账号同时进入 1109 排位房

#### Scenario: 最新有效连接接管原席位

- **WHEN** 同一账号连续建立多个满足重连条件的连接
- **THEN** 最后成功准入的连接成为该席位唯一活动连接，此前连接不能继续控制该席位

#### Scenario: 房间结束后释放占用

- **WHEN** 排位房正常完成、投降终局、重连超时终局或在开战前被清理
- **THEN** 服务器恰好一次释放房内所有玩家的活动排位房归属，使其可以再次进入任意格式的 `#TT`

#### Scenario: 服务重启后不存在僵尸占用

- **WHEN** 单实例服务进程重启并丢失全部内存房间
- **THEN** 先前房间的账号占用同时消失，账号可重新进入排位，且数据库中不存在需要人工清理的当前房间锁

### Requirement: 排位房支持账号级断线重连

已开战排位房必须（SHALL）保留断线玩家的原席位和不可变格式，并允许同一账号在既有 90 秒重连窗口内通过裸 `TT` 或对应格式的 `format#TT` 入口恢复；排位重连以有效账号身份为准，不要求来源 IP 保持相同，账号原房间优先于裸 `TT` 的默认 1109 映射。

#### Scenario: 单方在窗口内重连

- **WHEN** 已开战排位房的一名玩家断线，并在 90 秒内使用相同账号再次进入 `format#TT`
- **THEN** 服务器恢复其原位置、队伍、主机标志和当前对局阶段，且不创建新房、不重复计算比赛结果

#### Scenario: 断线窗口到期

- **WHEN** 已开战排位房的一名玩家连续断线 90 秒且对手仍保持连接
- **THEN** 服务器按该玩家超时投降结束比赛，并通过统一比赛终结流程记录一次有效胜负

#### Scenario: 双方断线且没有有效胜者

- **WHEN** 已开战排位房双方均在重连窗口届满前未恢复，且服务器无法得到唯一有效胜者
- **THEN** 服务器终结并清理房间，但不得（SHALL NOT）更新任何玩家的排位积分或胜负场次

#### Scenario: 等待阶段玩家离开

- **WHEN** 排位房尚未开战且等待中的玩家断开或主动离开，导致其不再占用玩家席位
- **THEN** 服务器释放该账号的房间占用，并且不记录比赛、不改变积分和胜负场次

### Requirement: 普通数字房保持匿名非排位行为

精确裸 `TT` 和已启用格式的 `format#TT` 必须（SHALL）是排位路由仅有的非数字入口；其他房间继续要求 `format#roomId` 中的 `roomId` 为非空十进制数字。普通数字房不得（SHALL NOT）因玩家提供 PIN 而自动变为排位房。

#### Scenario: 匿名玩家进入普通数字房

- **WHEN** 玩家不提供 PIN 并使用 `1103#1001` 或 `1109#1001` 加入
- **THEN** 服务器继续按既有匿名普通房逻辑创建或加入房间，且该房间不参与积分结算

#### Scenario: 数字房玩家提供 PIN

- **WHEN** 已认证玩家使用普通 `format#数字房间号` 加入
- **THEN** 服务器不得（SHALL NOT）仅因玩家具有账号而把该房间标记为排位房

#### Scenario: 普通数字房不写 PostgreSQL

- **WHEN** 任一普通 `format#数字房间号` 创建、进行或完成比赛
- **THEN** 服务器不得（SHALL NOT）创建账号、比赛、小局、统计、录像或其他 PostgreSQL 记录，并继续使用既有客户端录像发送行为

#### Scenario: 其他非数字房间标识

- **WHEN** 客户端使用裸 `tt`、`1103#tt`、`1103#ABC`、`1103#TT#extra`、空房间号或未启用格式
- **THEN** 服务器拒绝该连接，不创建、不查找且不修改任何房间

### Requirement: 排位结果按格式和自然月恰好结算一次

服务器必须（SHALL）只为具有唯一有效胜者的已完成真人排位 MATCH 更新统计，并以房间创建时绑定的 `format` 和 MATCH 结束时刻所属的北京时间自然月作为积分隔离键。月赛季标识必须（SHALL）使用 `YYYY-MM`；每名玩家在每个格式的每个新月赛季初始积分必须（MUST）为 0，首次结算时直接以该 MATCH 的积分变化创建统计行，之后每场积分变化必须（SHALL）等于该 MATCH 中自己的小局胜数减小局负数。只进入排位房但没有完成有效 MATCH 不得（SHALL NOT）创建 `player_stats` 行或进入排行榜。

#### Scenario: 新赛季首次有效比赛以二比零结束

- **WHEN** 两名玩家在某格式某月赛季都没有统计行，并以 2:0 完成该赛季首场有效排位 MATCH
- **THEN** 服务器创建双方月统计，胜者为 2 分、1 胜、0 负，败者为 -2 分、0 胜、1 负

#### Scenario: 1103 八月赛季以二比零结束

- **WHEN** 1103 排位 MATCH 在北京时间 2026 年 8 月以玩家 A 对玩家 B 的小局比分 2:0 完成
- **THEN** A 的 `2026-08` 赛季 1103 当前积分增加 2、胜场增加 1，B 的当前积分减少 2、负场增加 1；如果这是双方该赛季首场有效比赛，则结算后分别为 2 分和 -2 分，并保存带 1103 格式和 `2026-08` 赛季标识的比赛记录

#### Scenario: 1109 九月赛季以二比一结束

- **WHEN** 1109 排位 MATCH 在北京时间 2026 年 9 月以玩家 A 对玩家 B 的小局比分 2:1 完成
- **THEN** A 的 `2026-09` 赛季 1109 当前积分增加 1、胜场增加 1，B 的当前积分减少 1、负场增加 1；如果这是双方该赛季首场有效比赛，则结算后分别为 1 分和 -1 分，并保存带 1109 格式和 `2026-09` 赛季标识的比赛记录

#### Scenario: 跨月比赛归入结束月份

- **WHEN** 排位 MATCH 在北京时间 2026 年 8 月开始，并在 2026 年 9 月结束
- **THEN** 服务器只把该 MATCH 计入 `2026-09` 月赛季，不更新 `2026-08` 月赛季

#### Scenario: 同一账号在不同格式和月份独立计分

- **WHEN** 同一账号先后在不同北京时间自然月完成 1103 与 1109 排位比赛
- **THEN** 每场结果只更新对应 `format` 与 `YYYY-MM` 组合的统计，不产生跨格式或跨月份混合积分

#### Scenario: 重复终局事件

- **WHEN** 同一排位 MATCH 因重复消息或重叠清理路径产生重复终局通知
- **THEN** 服务器只保存并结算一次该 MATCH，双方月赛季统计要么同时成功更新，要么均不更新

#### Scenario: 非排位或无结果比赛

- **WHEN** 普通数字房结束、等待房未开战即关闭，或者排位房结束时没有唯一有效胜者
- **THEN** 服务器不更新任何格式、月份或总榜来源数据的排位积分与胜负场次

### Requirement: 排位对局只在整场终结后批量持久化

直接真人排位 MATCH 进行期间，服务器必须（MUST）只在房间内存中保留比赛、小局和录像生成所需记录，不得（SHALL NOT）写入任何比赛结果、小局详情、排位统计或录像数据。房间进入统一 MATCH 终结流程后，服务器必须（MUST）把有效比赛结果、每一小局详情、月度统计以及每一小局独立的原始 YGOPro 录像批量保存到 PostgreSQL，并保证同一有效比赛的全部写入原子且幂等。账号认证、自动注册和封禁查询不属于对局持久化，仍可在准入阶段访问数据库。

#### Scenario: 第一小局结束后进入换备

- **WHEN** 直接排位 MATCH 的第一小局正常结束，但整场尚未决出胜者并进入换备阶段
- **THEN** 服务器只把该小局记录和录像源数据保留在当前房间内存，不新增或更新任何比赛、小局、积分或录像数据库记录

#### Scenario: 二比一比赛整体批量保存

- **WHEN** 直接排位 MATCH 以 2:1 正常完成并进入统一终结流程
- **THEN** 服务器在一次原子批处理中保存双方比赛记录、三局小局详情、三份双方共享的独立录像以及双方月度积分；这些数据必须全部成功或全部不生效

#### Scenario: 每一小局只保存一份原始录像

- **WHEN** 一个有效排位 MATCH 包含多局已经正常结束的小局
- **THEN** 服务器按小局顺序为每一小局恰好保存一份可还原为 `.yrp/.yrp2` 文件的原始录像，双方的小局详情共同关联该份录像，不保存 YGOPro 网络帧头且不重复保存双方副本

#### Scenario: 重复执行整体终结

- **WHEN** 同一排位 MATCH 的统一终结流程因重复消息或一次失败后的重试而再次执行
- **THEN** 服务器使用稳定比赛标识和小局序号识别已处理数据，不重复保存录像、小局和比赛，也不重复累加积分或胜负场次

#### Scenario: 批量写入中途失败

- **WHEN** 有唯一有效胜者的排位 MATCH 在批量保存比赛、小局、录像或任一玩家统计时发生数据库错误
- **THEN** 服务器回滚本次全部对局写入，并使用同一稳定标识立即重试一次；重试仍失败时不得留下部分比赛、部分录像或单方积分

#### Scenario: 无有效胜者但已有完成的小局

- **WHEN** 直接排位房最终没有唯一有效胜者，但在终结前已经存在一局或多局正常结束且可序列化的小局
- **THEN** 服务器只在统一终结时批量保存这些小局的独立录像，不保存有效比赛结果、不更新任何排位积分或胜负场次

#### Scenario: 普通数字房完成比赛

- **WHEN** 普通 `format#数字房间号` 完成包含一局或多局的 MATCH
- **THEN** 服务器保持既有客户端录像发送行为，但不得（SHALL NOT）执行任何 PostgreSQL 写入

#### Scenario: MATCH 终结前服务进程退出

- **WHEN** 直接排位 MATCH 尚未进入统一终结流程时服务进程退出并丢失房间内存
- **THEN** PostgreSQL 中不存在该 MATCH 的部分比赛、小局、积分或录像记录，服务重启后不恢复这些未落库数据

### Requirement: 排位 PostgreSQL 使用最小初始化基线

首次正式启用的排位 PostgreSQL 必须（MUST）由一个面向空库的初始化 Migration 创建；该基线必须（MUST）只创建 `users`、`user_bans`、`matches`、`duels`、`player_stats` 和 `duel_replays` 六张业务表。TypeORM 自身维护的 Migration 元数据表不属于业务表。旧 Migration 历史必须（MUST）在生成该基线前删除，后续模式更新必须（MUST）追加新的 Migration，不得（SHALL NOT）反复改写或压平已上线的初始化 Migration。

#### Scenario: 空库应用初始化 Migration

- **WHEN** PostgreSQL 在空数据目录完成 `init.sql` 扩展初始化，运维人员首次执行生产 Migration runner
- **THEN** 数据库只包含六张排位业务表和 TypeORM Migration 元数据表，并且 `matches.format_id`、`player_stats.format_id` 与 `duels.replay_id` 均为非空字段

#### Scenario: 初始化基线排除历史非排位表

- **WHEN** 检查初始化 Migration、DataSource 注册实体或首次迁移后的空库结构
- **THEN** 不得（SHALL NOT）出现 `tournaments`、`achievements`、`user_achievements`、`lightning_tournaments`、`lightning_rankings`、`lightning_results`、`unranked_matches`、`unranked_duels`、`stats_daily_summary` 或其相关触发器

#### Scenario: 后续发布追加模式变更

- **WHEN** 初始化基线已经在任一排位环境执行，后续版本需要修改数据库结构
- **THEN** 开发者基于当前实体生成并提交新的增量 Migration，运维人员在升级服务前显式执行它，且不得修改已应用的初始化 Migration

### Requirement: 排行榜 API 按格式提供月赛季榜和总榜

服务器必须（SHALL）公开无需登录即可访问的 `/api/leaderboards/:format` 查询接口。当前必须（SHALL）支持 1103 与 1109；每种榜单响应必须至少包含排名、昵称、积分、胜场和负场，并且不得（SHALL NOT）混入其他格式的数据。排行榜 HTML 页面及其交互不属于本能力，由独立前端变更消费该 API。

#### Scenario: 查询指定月份赛季榜

- **WHEN** 用户请求 `/api/leaderboards/1103?scope=season&season=2026-08`
- **THEN** 响应只包含 `2026-08` 月赛季至少完成过一场有效 1103 排位 MATCH 的账号及该月统计，不混入其他月份或格式

#### Scenario: 查询历史总榜

- **WHEN** 用户请求 `/api/leaderboards/1103?scope=overall`
- **THEN** 响应按账号汇总全部月份的 1103 月赛季积分、胜场和负场，每场已结算 MATCH 恰好贡献一次，并且不混入 1109 或其他格式

#### Scenario: 同一账号的总榜等于月榜之和

- **WHEN** 一个账号在同一格式的多个自然月拥有月赛季统计
- **THEN** 该账号总榜的积分、胜场和负场分别等于这些月份对应字段之和，服务器不维护可能与月榜不一致的第二份累计积分

#### Scenario: 没有比赛的有效月份

- **WHEN** 用户查询格式正确但没有任何有效比赛的历史月份
- **THEN** 服务器返回该格式与月份的空排行榜，而不回退到当前月份或总榜

#### Scenario: 排名顺序稳定

- **WHEN** 月赛季榜或总榜包含多个账号
- **THEN** 服务器先按积分降序、再按胜场降序、最后按昵称升序产生稳定名次

#### Scenario: 排行榜查询参数无效

- **WHEN** API 请求缺少有效 `scope`、月榜缺少合法 `YYYY-MM`，或同时使用不兼容的查询参数
- **THEN** 服务器返回明确的请求错误，不回退到默认月份、总榜或其他格式

#### Scenario: 访问未启用格式

- **WHEN** 用户访问未在固定格式注册表中启用的排行榜格式
- **THEN** 服务器返回明确的格式不存在响应，且不回退到 1103、1109 或跨格式全局排行榜

#### Scenario: 新格式复用排行榜实现

- **WHEN** 应用以后显式注册新的固定怀旧格式并产生该格式的排位统计
- **THEN** 同一路径、scope、月份参数和返回字段可以查询该格式月赛季榜与总榜，不需要复制格式专用 controller 或数据表
