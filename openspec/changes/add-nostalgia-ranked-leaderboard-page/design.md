## Context

动机参见 [proposal.md](./proposal.md)。项目当前没有独立前端工程或浏览器构建链；现有根页面由 Express controller 直接返回自包含 HTML、CSS 和原生 JavaScript。排位后端变更 `add-direct-nostalgia-ranked-rooms` 将提供公开的参数化 JSON API：

- `GET /api/leaderboards/:format?scope=season&season=YYYY-MM`
- `GET /api/leaderboards/:format?scope=overall`

本变更只在该契约之上增加浏览器页面，不接触排行榜查询、积分结算或数据库模式。

## Goals / Non-Goals

**Goals:**

- 用一个参数化页面覆盖 1103、1109 和以后显式启用的固定格式。
- 用项目现有 HTTP 交付方式提供无需登录的总榜/月榜浏览体验。
- 明确处理当前北京时间月份、加载、空榜、失败、排位关闭与未知格式。
- 保持页面小而自包含，不增加前端构建和运行依赖。

**Non-Goals:**

- 不修改排行榜 API、排序规则、赛季计算、积分持久化或数据库表。
- 不新增登录、个人中心、录像列表、分页、搜索、缓存或实时推送。
- 不引入 React、Vue、模板引擎、CSS 框架、外部字体或 CDN 资源。
- 不把 1103 与 1109 拆成两份 HTML、controller 或脚本。

## Decisions

### 1. 延续自包含页面 controller

新增独立的排行榜页面 controller，由 `GET /leaderboards/:format` 返回一份参数化、自包含的 HTML/CSS/原生 JavaScript。页面通过同源 `fetch` 消费排行榜 API，路由只注册一次。

该方式与现有 `InspectPageController` 的交付模型一致，不需要 npm 前端依赖、构建产物复制或第二个部署服务。页面代码必须保持单一职责；若以后演化为多页面应用，再以独立变更评估前端工程化。

备选方案是引入 SPA 工程或服务端模板引擎。当前只有一个只读页面，新增工具链和依赖不符合最小实现原则，因此不采用。

### 2. 服务端先校验排位开关和格式

页面 controller 在返回 HTML 前先检查 `RANK_ENABLED` 和固定格式注册表：排位关闭返回明确不可用响应，未知格式返回 404；只有已启用格式才渲染页面。格式值作为经过白名单验证的数据注入页面，浏览器不从任意路径字符串推断后端地址。

这样可以避免先返回一个看似可用的页面，再由 API 错误暴露真实状态，也防止页面静默回退到其他格式。

备选方案是始终返回通用 HTML 并完全依赖 API 报错。它会让关闭与未知格式的首屏语义含糊，因此不采用。

### 3. 当前月固定按 Asia/Shanghai 计算

页面首次加载月榜。浏览器使用支持显式 `timeZone: "Asia/Shanghai"` 的日期格式化能力得到 `YYYY-MM`，不使用用户设备本地月份；月份控件只产生严格 `YYYY-MM`。总榜请求不携带 `season`，月榜请求必须携带当前选择的 `season`。

备选方案是使用浏览器本地月份。境外用户或系统时区错误会在月末打开错误赛季，因此不采用。

### 4. 用单一页面状态驱动请求和渲染

页面状态只包含 `formatId`、`scope`、`season`、加载状态和最后一次请求序号。每次切换 scope 或月份都递增序号；响应只在序号仍为最新时渲染，从而避免慢响应覆盖新选择。失败时清空旧表格并保留当前选择，重试按钮重复同一请求。

DOM 通过 `textContent` 创建单元格，禁止把昵称拼入 `innerHTML`。API 数据只用于展示，页面不读取账号 ID、PIN、密码或录像字段。

备选方案是增加状态管理库和客户端缓存。数据量与交互都很小，原生状态足够，也避免缓存造成榜单过期。

### 5. 页面与后端 API 通过契约测试保持一致

页面只依赖 API 的 `format`、`scope`、可选 `season` 和排行项 `rank/name/points/wins/losses`。controller/路由测试固定以下边界：有效格式返回页面、未知格式拒绝、排位关闭不可用、页面只引用参数化 API 且不包含敏感字段。浏览器脚本保持小型函数结构，使请求 URL、北京时间月份、过期响应忽略和纯文本渲染逻辑可以在不新增 DOM 测试依赖的前提下接受聚焦测试或固定契约验证。

备选方案是只做人工浏览器验证。它无法稳定覆盖格式隔离和关闭状态，因此仍需自动化 controller/脚本契约测试，最终再做真实浏览器宽度的人工验收。

## Risks / Trade-offs

- [内联 HTML/CSS/JavaScript 随功能增长会难以维护] → 严格限制为只读排行榜页面；出现第二个复杂页面时再评估静态资源或前端工程。
- [页面与尚未落地的排行榜 API 可能产生契约偏差] → 后端排位 change 先实现并固定 API，页面测试使用同一字段和错误行为，部署顺序明确为后端优先。
- [浏览器本地时区导致月份错误] → 显式使用 `Asia/Shanghai` 并覆盖月末边界测试。
- [快速切换导致旧响应覆盖新结果] → 为请求分配递增序号，仅渲染最后一次选择。
- [玩家昵称可能形成 XSS] → 所有用户数据使用 `textContent`，不允许排行项进入 `innerHTML`。
- [窄屏表格字段过多] → 保留完整表格语义并允许横向滚动，不隐藏排名或胜负字段。

## Migration Plan

1. 先完成并验证 `add-direct-nostalgia-ranked-rooms` 中的排行榜 API，确认 1103/1109、月榜、总榜、空榜和错误响应稳定。
2. 增加页面 controller、单一路由和自动化契约测试，不修改数据库或排位启动流程。
3. 在 `RANK_ENABLED=true` 环境验证 1103/1109 当前月、历史月、总榜、空榜和 API 失败状态；在 `RANK_ENABLED=false` 与未知格式下验证明确拒绝。
4. 在桌面和不超过 480 像素的窄屏完成页面验收，并确认昵称按纯文本渲染。
5. 随同普通应用镜像部署，无需 Migration 或独立前端服务。回滚时恢复上一应用镜像即可，数据库和排行榜 API 不受影响。
