## Purpose

定义怀旧环境标识与玩家房间号共同构成的加入契约，使玩家和观战者仅凭 `format#roomId` 选择正确裁定环境并进入同一房间，同时保证不同环境的同号房间彼此隔离。

## ADDED Requirements

### Requirement: 使用环境化房间标识加入

服务器必须（SHALL）将完整的 `format#roomId` 解释为怀旧环境房间标识，其中 `format` 必须是已启用的 1103 或 1109，`roomId` 必须是非空十进制数字，并且完整值必须适配 YGOPro `JoinGame` 的 20 个 UTF-16LE 字符槽。

#### Scenario: 首位玩家创建 1103 房间

- **WHEN** 尚不存在该房间时，玩家使用 `1103#1001` 加入
- **THEN** 服务器创建环境为 1103、外部房间号为 1001 的房间，并将该玩家加入房间

#### Scenario: 首位玩家创建 1109 房间

- **WHEN** 尚不存在该房间时，玩家使用 `1109#1001` 加入
- **THEN** 服务器创建环境为 1109、外部房间号为 1001 的房间，并将该玩家加入房间

#### Scenario: 次位玩家加入同一环境房间

- **WHEN** 某环境房间已存在时，另一玩家使用完全相同的 `format#roomId` 加入
- **THEN** 服务器将其加入现有房间，而不是创建新房间

### Requirement: 环境房间不使用密码

服务器必须（SHALL）把 `#` 右侧内容完整解释为外部 `roomId`，不得（SHALL NOT）将其用于房间口令校验；同一环境和 `roomId` 的玩家或观战者无需提供额外密码即可相遇。

#### Scenario: 房间号不是认证凭据

- **WHEN** 两名玩家先后使用 `1103#1001` 或先后使用 `1109#1001` 加入
- **THEN** 服务器仅按环境化房间标识匹配两名玩家，不执行旧的房间密码比较

### Requirement: 房间身份包含环境标识

服务器必须（SHALL）使用 `format` 与 `roomId` 的组合标识查找和持有房间，内部生成的全局 ID 可以继续用于生命周期管理，但不得（SHALL NOT）以裸 `roomId` 代替环境化身份。

#### Scenario: 1103 与 1109 使用相同房间号

- **WHEN** 客户端分别使用 `1103#1001` 和 `1109#1001` 加入
- **THEN** 服务器创建或查找两个相互独立的房间，任何玩家或观战者均不能跨环境进入另一房间

### Requirement: 双环境采用各自固定规则

服务器必须（SHALL）将 1103 映射为 OCG 2011.03 禁限卡环境，将 1109 映射为 OCG 2011.09 禁限卡环境；两个环境均使用 Master Rule 2 和 MATCH 模式（8000 LP、三局两胜），并在房间创建后保持环境选择不可变。

#### Scenario: 创建 1103 对局

- **WHEN** 玩家通过有效的 `1103#<roomId>` 创建房间
- **THEN** 房间使用 1103 最终卡池、Master Rule 2、MATCH 模式、固定 OCG 2011.03 禁限卡表和 1103 脚本查找链

#### Scenario: 创建 1109 对局

- **WHEN** 玩家通过有效的 `1109#<roomId>` 创建房间
- **THEN** 房间使用 1109 最终卡池、Master Rule 2、MATCH 模式、固定 OCG 2011.09 禁限卡表和 1109 脚本查找链

#### Scenario: 已存在房间保持原环境

- **WHEN** 玩家或观战者加入一个已存在的环境化房间
- **THEN** 服务器沿用该房间创建时绑定的卡池、规则、禁限卡表和脚本集合，不根据后续连接重新解释

### Requirement: 环境化路由保持现有观战语义

服务器必须（SHALL）让使用相同 `format#roomId` 加入既有房间的连接继续经过现有房间状态判定，以识别玩家、符合条件的重连玩家或观战者；环境化路由不得（SHALL NOT）绕过或改变观战准入、消息可见性、席位和房间生命周期规则。

#### Scenario: 第三个客户端观战既有房间

- **WHEN** 两个玩家已经占用 `1103#1001` 或 `1109#1001` 的玩家席位，第三个客户端使用相同环境化房间标识加入
- **THEN** 服务器按现有规则将第三个客户端作为观战者加入，且不占用或替换玩家席位

#### Scenario: 在不同对局阶段加入观战

- **WHEN** 客户端在等待、猜拳、先后手选择、决斗中或换备阶段使用相同环境化房间标识加入既有房间
- **THEN** 服务器按该阶段既有观战行为恢复可公开的历史视图并继续发送实时观战消息，不向观战者泄露仅玩家可见的消息

#### Scenario: 重连玩家优先恢复席位

- **WHEN** 符合现有重连条件的玩家与普通观战加入发生在环境化房间中
- **THEN** 服务器按现有重连规则恢复该玩家席位，不因新路由将其降级为观战者或让观战者占用其席位

#### Scenario: 观战者断开连接

- **WHEN** 环境化房间中的观战者断开连接
- **THEN** 服务器只更新该房间的观战连接状态或人数，不结束房间、不改变玩家状态也不影响另一环境的同号房间

#### Scenario: 等待中的观战者转为玩家

- **WHEN** 现有房间规则允许等待状态中的观战者转为玩家
- **THEN** 环境化房间继续执行既有转席行为，并保持原 format、roomId、卡池和裁定不变

### Requirement: 拒绝无效或未启用环境

服务器必须（SHALL）拒绝未知 `format`、空 `roomId`、非数字 `roomId`、额外分隔段或超过线协议长度上限的环境化房间标识，并且不得（SHALL NOT）创建任何房间。

#### Scenario: 未启用环境加入

- **WHEN** 客户端使用除 1103 和 1109 之外的四位环境标识加入
- **THEN** 服务器返回兼容的加入失败结果并关闭本次连接，且不创建房间

#### Scenario: 房间标识格式非法

- **WHEN** 客户端使用 `1103#`、`1109#abc`、`1109#1001#secret` 或超过协议字符槽的值加入
- **THEN** 服务器拒绝该请求，不创建或修改房间，也不把输入回退为旧式名称/密码语义
