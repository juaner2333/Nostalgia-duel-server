## Context

动机见 [proposal.md](./proposal.md)，行为契约见 [spec](./specs/nostalgia-half-year-deck-winrate-matrix/spec.md)。现有 `matches` 每场通常有两条玩家视角行，`match_decks` 保存 G1 前可信快照与类别；`usage_stat_runs`、`usage_deck_rows` 已按北京时间自然半年统计卡组使用量，使用率任务目前在 03:10 执行。`duels` 尚无 `duel_index` 和 `is_first`，不能从 Match 胜负或 G2/G3 结果推测 G1 座次。`docs/deck-statistics-system-plan.md` 的月度三表结构是当时的目标方案；本服务已实现其中使用量与发布批次的半年版，因此只需新增对阵明细并扩展现有批次。

## Goals / Non-Goals

**Goals:**

- 从现有半年使用量批次确定前 16 名，并在同一事务发布该名单对应的 Match 矩阵，结果可复算。
- 把 G1 座次作为明确的比赛事实落库，确保先后攻胜率有可证明来源。
- 后台原子替换可重建汇总，公开请求只读已发布整数计数。

**Non-Goals:**

- 不新增 1103 具名分类、Game/Main/Side 小局胜率、卡组详情或玩家榜单。
- 不改变既有半年度使用率 API、分类规则、Match 积分与 `.yrp` 二进制格式。

## Decisions

### 1. 半年窗口和前 16 名从同一读取批次产生

将现有 `rebuild:usage` 的计划启动时间从 03:10 调整到北京时间 03:00。对 1109，该任务在一个一致性读取中以 `matches.date` 的 `[window_start, data_end_exclusive)` 范围取得有效事实，先按既有规则计算 `usage_deck_rows`，再从同批内存计数去掉 `OTHERS`，按 `deck_count DESC, deck_type_code ASC` 选最多 16 类，零份数不入选。对阵计算复用同一读取版本与截止日；1103 的使用率计算保持现状。`matches.season` 仅作边界交叉核验，不替代半年日期范围。已有无时区 `matches.date` 的写入语义须沿用半年度使用率已验证的北京时间转换，并用跨 6 月/7 月、12 月/1 月的 PostgreSQL 样本复核。

备选是保留 03:10 使用率任务，并在 03:00 用独立任务重复计算、存储半年使用量。这样多出一份排名事实与第二个发布时机；本期改为同一计划任务和发布批次。

### 2. 在对局开始时冻结 G1 座次，而不从比分倒推

为 `duels` 增加可空 `duel_index smallint` 与 `is_first boolean`；新 1109 排位在每局真正启动时，将引擎实际先手与稳定玩家身份关联，并随 `GameOverDomainEvent` 的每局记录传到原有结算事务。`duel_index` 对应 G1/G2/G3，`is_first` 表示该局真实先手；提前终结且未开局的伪造结果保留 `NULL`。双方确有 G1 时应形成一真一假的两个玩家视角事实。领域事件仅增补元数据，仍由现有显式统计订阅流程恰好一次持久化，不引入新的订阅副作用。

历史回填先只读预演：按 `duels.replay_id` 关联真实 `duel_replays`，核对 `game_id`、1109 赛制、所属 Match、双方身份及唯一性。G1/G2/G3 的 `duel_index` 只从验证后的 `duel_replays.duel_index` 复制；`is_first` 另由已人工核对的固定二进制样本证明录像玩家顺序与真实先手的对应关系，再解析该小局录像并唯一映射到玩家视角。只有编号可靠时可单独回填编号，先手仍为 `NULL`；两方座次同时可信才原子写入一真一假，G1 才可进入矩阵。缺失、占位或损坏录像及冲突行保持未知并报告原因；不能从 `winner`、固定玩家席位或 `replay_id` 非空推断。回填复用现有排位库连接安全边界，按物理 Match 原子、幂等写入，不覆盖在线可信值。

备选是从 `.yrp` 的 host/client 字段直接推断全部历史座次；该顺序是否等于实际先手必须先由独立固定样本证明，因此不作为默认路径。

### 3. 复用发布头与使用量，只新增物理 Match 对阵表

具体目标结构见 [DDL](./specs/nostalgia-half-year-deck-winrate-matrix/ddl.sql)：

| 表 | 本次变更 | 用途 |
| --- | --- | --- |
| `usage_stat_runs` | 不改表 | 继续保存半年边界、实际截止日、发布时间与使用量分母 |
| `usage_deck_rows` | 不改表 | 按既有半年使用份数选前 16；`OTHERS` 保留在使用率榜但不入选 |
| `stats_deck_matchups` | 新建 | `(format_id, window_start, first_deck_code, second_deck_code)` 唯一的一行物理 Match 计数与先攻胜场 |

新对阵表只允许 `format_id='1109'`，只存双方均入选的类别，满足 `match_count > 0` 与 `0 <= first_wins <= match_count`，不存率、不存反向行。前 16 类之间入选的物理 Match 总数直接取对阵行的 `COALESCE(SUM(match_count), 0)`，包括零行时返回 0；发布时间沿用现有 `usage_stat_runs.published_at`。不在 `usage_stat_runs` 增加对阵字段。

发布前校验对阵行的 `COALESCE(SUM(match_count), 0)` 与本批次计算得到的入选物理 Match 数相等、前 16 名按本批次 `usage_deck_rows` 的数量稳定排序且不含 `OTHERS`，并保留现有使用量和卡片计数校验。`OTHERS` 与第 17 名仍可计入使用量，但不进入对阵表。`stats_deck_matchups` 的外键仅关联现有 `usage_stat_runs` 批次与环境内 `deck_types`；前 16 名成员关系由同一批次的计算和发布校验保证。迁移由 TypeORM 实体生成并与目标 DDL 对照审阅，不编辑已应用迁移。

备选是另建 `stats_deck_usage` 和 `stats_deck_coverage`；当前服务已有同粒度的半年使用量明细与发布头，这两张新表会重复事实，所以删除该设计。

### 4. 以两个方向的物理行构造一个玩家视角单元

对不同类别 X/Y，`(first_deck_code=X, second_deck_code=Y)` 这一行给出 X 对 Y 的先攻胜率 `first_wins / match_count`；反向 `(Y,X)` 这一行给出 X 对 Y 的后攻胜率 `(match_count - first_wins) / match_count`。综合胜率先把两方向的胜场和场数分别相加，再相除。对内战 `(X,X)`，物理行仍只有一份，返回玩家视角综合 `2*match_count` 场、`match_count` 胜；先攻与后攻各有 `match_count` 场。所有百分比在查询或页面由整数计数计算，零分母为 `null`；不存率、不平均率。每行“前 16 内合计”仅加总该行对所有入选类别的玩家视角计数，包含内战的双视角，不包含任何名单外对局。

备选是预存双向玩家视角行和 `ALL` 行，会让单场内战与总计更易重复计数，因此沿用 RFC 的单行事实。

### 5. 一次性 CLI、短事务发布和只读查询

沿用现有一次性 `rebuild:usage` 命令及宿主 crontab，将计划时间调整为北京时间 03:00；宿主为 UTC 时换算到前一日 19:00。任务仍默认重建当前半年并补齐上一半年，`--period=YYYYH1|YYYYH2` 继续用于人工回填。上线时须对全部已有 1109 使用率半年批次执行统一重建，上一半年即使使用率已达到最终截止日也要重建矩阵。在线进程启动与 HTTP 查询均不触发全量计算。1109 沿用现有 PostgreSQL advisory lock；使用量、卡片与对阵在同一一致性读取下计算、校验，再在一个短事务内原子替换相应批次的 `usage_stat_runs`、`usage_deck_rows`、`usage_card_rows` 与 `stats_deck_matchups`。失败回滚并保留上次成功的全部结果；1103 仍按原有独立批次发布。

公开 `GET /api/ladder/:format/deck-stats` 和 `.../periods` 只读取已提交的同一批次；在全部已有 1109 半年完成统一重建后，现有 `usage_stat_runs` 批次行即代表对应半年已发布，缺行视为未就绪，存在批次但对阵零行视为零样本。响应结构沿用 RFC 的 `decks` + `stats["X::Y"]` 六计数字段，并增加窗口、截止日、从对阵行求和得到的入选物理场数及入选使用份数。`stats` 只包含前 16 名的有序对；无对局单元填零计数。页面路径 `/leaderboards/1109/deck-stats`，页面标题与顶栏 Tab 均为「卡组胜率」；在 1109 决斗专区的既有顶栏中，它与「房间列表」「录像下载」「天梯排行」「使用率」同级，使用率页面也显示通往它的同级 Tab，新页面将本 Tab 标为选中。1103 不显示该 Tab。`X::TOP16` 是查询层生成的行合计，不在库中存 `ALL` 行。半年和三种视图在 URL 可恢复，页面仅用原始计数计算百分比并展示胜场/场数、入选对阵场数、更新时间和旧数据状态。继续沿用现有公开接口限流与 `ranking.enabled` 检查。

备选是在请求时直接扫描 `matches`、`duels` 与快照；查询时间及结果会随库增长和后台修正波动，也无法保证一个页面使用同一发布批次。

## Risks / Trade-offs

- [历史 G1 座次无法全量证明] → 回填只采纳独立样本和无歧义映射；批处理报告跳过原因及数量，页面只展示实际入选的对阵场数。
- [旧使用率批次与零对阵均无对阵行] → 公开矩阵前统一重建全部已有 1109 半年；只保留合并后的唯一计划任务，旧版使用率任务运行后重新重建受影响半年。
- [前 16 名随半年内使用量变动] → 每次重建在同一事务原子替换名单和矩阵；历史页面读取各自发布名单，不能把当前名单套到过去半年。
- [合并任务扩大 1109 单次重建工作量] → 有界读取且不扫描录像字节；对阵计算和发布失败时让 1109 使用率与矩阵一同保留上一完整批次，分别报告失败类别。
- [历史无时区 `matches.date` 边界或分类版本混杂] → 复用半年度使用率已验证的时间语义；分类规则升级先按原流程重分类可信快照，再人工重建受影响半年。
- [半年全量读取影响在线 PostgreSQL] → 使用现有范围索引和有界游标，避开录像字节读取；上线前用接近真实数据量核对查询计划、任务耗时与内存。

## Migration Plan

1. 为 `duels` 新增可空座次列和必要索引，并新增一张对阵表；`usage_stat_runs` 与 `usage_deck_rows` 不改表。运行生成迁移并在隔离 PostgreSQL 验证升级与回滚。
2. 上线新对局 G1 座次采集，并扩展现有 `rebuild:usage` 命令与发布事务；用固定 Match、内战、半年边界、历史未知座次样本完成单元与 PostgreSQL 集成验证。
3. 对历史 G1/G2/G3 录像先做只读预演并审核编号及座次各自的可确认比例，再幂等回填可信字段；在公开矩阵接口前统一重建全部已有 1109 使用率半年批次，核对前 16、入选对阵场数、胜场/场数及页面。
4. 确认任务结果后把现有 03:10 crontab 改为唯一的 03:00 条目，防止两条任务同时运行。回滚时恢复与回退镜像匹配的调度配置，保留原始比赛事实与可重建汇总，不修改已应用迁移或删除历史快照；若旧版仅使用率任务运行过，重新启用矩阵接口前先重建其影响的 1109 半年。
