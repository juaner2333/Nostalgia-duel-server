## Context

动机见 [proposal.md](./proposal.md)，行为契约见 [玩家详情规格](./specs/nostalgia-player-detail/spec.md) 与 [昵称入口增量](./specs/nostalgia-ranked-leaderboard-page/spec.md)。本变更涉及查询聚合、密码验证和历史分页，需要在实现前明确权限及统计边界。

- 现有浏览器页面由 HTTP Controller 返回独立 HTML，样式与交互脚本内嵌；无独立前端构建或组件框架。
- 天梯将按月保存的 `player_stats` 聚合为半年或总榜，排序为积分降序、胜场降序、昵称升序。`matches` 一场排位 Match 保存双方各自视角，记录比分和本场积分变化；`duels` 保存小局索引、先后手及录像关联。
- `match_decks` 以玩家视角 Match ID 保存 G1 初始卡组，`deck_types` 按环境定义类型。1103 暂只有「其他」；快照缺失与历史先后手未知是允许的实际状态。
- 现有 `UserProfileRepository.findByUsername` 和 `UserProfile.isValidPassword` 可以复用账号与 bcrypt 密码验证。本服现有排位密码/PIN 是此处验证的凭据，不引入另一套详情页密码。
- 公共 `RateLimitMiddleware` 依赖可选 Redis，并在不可用时放行；新增密码验证不能仅依赖此中间件。
- `add-replay-deck-access` 已有代码和验收记录，但其发布及生产回填任务尚未完成；本设计只依赖相应代码与迁移，不假设所有生产历史已有卡组快照。

## Goals / Non-Goals

**Goals:**

- 使用现有事实和统计口径查询详情，公共 DTO 不包含账号敏感字段。
- 将权限验证与有界历史查询放在应用用例中，领域负责输入范围、比例及统计规则，HTTP 只负责传输与页面。
- 提供可复核的 G1 次数、完整分页和积分累计，避免连接小局或双方视角造成重复场次。

**Non-Goals:**

- 不改变现有结算、天梯接口、公开录像和公开 YDK 下载权限；详情页的二十条限制只约束新增详情历史接口，不承诺现有其他公开入口隐藏旧录像。
- 不增加账号会话、JWT、Redis 强制依赖、统计汇总表、卡组分类器、猜拳采集或本次专用历史回填。
- 不配置云端证书、执行生产迁移或部署；发布环境须使用已有 HTTPS 入口提交密码。

## Decisions

### 1. 延续独立 HTML 页面与共享统计查询模块

新增 `PlayerDetailPageController`、`GetPlayerDetailController` 和 `/leaderboards/:format/player`，通过 `POST /api/ladder/:format/player` 查询公开及验证模式。两种模式共享请求结构，密码仅在正文中存在。响应按 HTTP 模块局部规则使用 `{ success, data?, error? }`，既有接口保持现有响应结构。

在 `src/shared/stats/player-detail/{domain,application,infrastructure/postgres}` 定义领域 DTO、查询端口、`GetPlayerDetail` 用例及适配器，通过构造函数注入查询端口、`UserProfileRepository` 和密码失败计数端口。领域不导入 HTTP 或数据库；基础设施只查询现有数据库，不调用客户端模块。复用 `calculateBeijingSeason` 的半年解析及既有用户验证；新增 DTO 每个字段必须有中文说明。

备选是扩展现有排行榜用例承担完整详情，或引入 SPA。前者会把排行与本人验证、比赛历史职责混合；后者需要新的构建链，均无必要。

### 2. 范围、页面布局与请求契约

查询正文包括 `player`、可选 `password`、`scope`、可选 `season` 和 `page`。缺省 `scope=season`，缺省赛季为北京时间当前半年；`scope=overall` 不接受赛季参数。`scope` 和 `season` 只控制战绩与卡组统计，`page` 对应全时期历史。每页固定 20 条，不提供扩大分页大小的参数；忽略未知分页大小参数并按固定上限处理，不通过客户端标志决定验证状态。

页面网址只同步 `player`、`scope`、`season`、`page`。统计范围切换保留全时期历史页码；切换玩家重置为第 1 页。半年模式同时显示总摘要、总卡组统计、半年摘要与半年卡组统计，总战绩模式只显示总摘要及总卡组统计。两组卡组与 G1 统计各自使用完整有效范围；历史、记录积分和曲线统一使用全时期数据。曲线以当前环境的玩家当前总积分为终点，固定倒推全时期最近最多 20 场，不随统计范围或历史页码变化；半年没有记录时只使半年摘要和半年卡组为空，全时期历史及曲线仍可展示。查询框按第一个 `$` 拆分「昵称$密码」，提交后只显示昵称；只提交昵称清除密码，跨玩家跳转清除密码，范围切换和翻页可复用当前内存凭据。

布局参考用户提供的 [玩家战绩页面](http://121.4.34.71:7922/player-stats.html?player=%E9%9A%90%E8%BA%AB%E8%93%91&month=202609&page=1)：顶部保留查询与周期控件，主体统计卡内以玩家名称开头，按「总战绩 → 总使用率 → 半年战绩 → 半年使用率 → 积分变化」排列，后面以独立卡片展示最近战绩。战绩使用指标卡片网格，使用率模块使用卡组统计表；在窄屏上指标自动换行、表格可横向滚动。参考页的月度模块及月份控件替换为半年赛季，不复制其语言切换、猜拳字段或外部资源引用。颜色、字体和品牌复用本项目现有页面，不新增前端依赖。

`data` 包含玩家公开昵称、格式、有效统计范围、验证模式、总摘要、总卡组统计、可选半年摘要及半年卡组统计、全时期曲线、全时期历史行及有效分页；DTO 明确区分总统计与半年统计，历史及曲线的范围固定为 `overall`。玩家不存在返回成功的 `found=false` 业务状态；已有玩家但所选半年无比赛时，仅半年摘要归零、半年卡组为空，总统计、全时期历史及曲线仍返回可用数据。API 错误使用 400，未启用格式 404，排位关闭 503，验证限流 429。响应加 `Cache-Control: no-store`。

参考页提供布局依据，统计周期仍采用已确认的半年赛季。历史不随统计周期筛选，曲线以当前总积分为终点，页面需清楚标明全时期最近二十场的倒推口径。

### 3. 在查询完整历史之前验证目标玩家密码

用例先校验公开参数并精确查找玩家，再处理可选密码。带密码时先检查来源与目标玩家的失败预算，再调用既有 `isValidPassword`；验证成功才允许全时期完整历史的计数和分页读取。每次完整历史请求独立验证，不引入 Cookie 或令牌。失败与不提供密码均查询全时期固定的最新最多 20 条，返回有效 `page=1`、`pageSize=20`、`total=可见条数`，前端据此修正网址并显示公开提示。摘要及卡组统计使用各自完整统计范围，记录限制不改变聚合数据；切换统计范围也不能改变公开记录集合或绕过上限。

密码只能存于当前页面的闭包内存，不能写入 URL、DOM 数据属性、浏览器持久存储或日志。每次重新提交仅昵称即解除验证；切换玩家、跳转对手、页面重新载入均清除。来源信息只供失败计数使用，不进入 DTO。错误处理和 Logger 不记录请求正文或用户实体。

复用既有 `isRateLimited` 使用的计数存储形状，在密码验证路径增加独立失败预算：同一来源与规范化目标昵称在 60 秒内允许最多 5 次失败；失败次数达到上限后再次验证返回 429，成功后清理该失败计数。Redis 可用时共享计数；无 Redis 或计数存储故障时使用带到期清理的进程内计数，限制仍生效。只限制带凭据验证，不阻断无密码公开查询；公共读取继续使用既有公开限流。计数变化及回退需要中文注释说明边界，不扩展其他接口限流行为。

备选是新建登录会话或把密码放入 GET 查询参数。会话引入生命周期与撤销成本，GET 则会暴露凭据，均不采用。浏览器的验证标记也不能作为服务器授权依据。

### 4. 摘要复用天梯统计，明细基于有效玩家视角 Match

总摘要和半年摘要从现有 `player_stats` 汇总，并沿用现有天梯全量排序后再精确选中玩家的名次；用有界返回的查询取得所需玩家，不在 Node 中下载全榜。复用既有排名规则，避免用昵称模糊搜索结果中的第一条作为目标。

历史、卡组及曲线查询以 `matches.user_id`、`format_id` 为基准，过滤 `anulled=false` 和 `deleted_at IS NULL`。只有卡组统计应用所选统计范围；历史、记录积分和曲线不添加半年过滤条件，统一使用当前环境全时期比赛。每个玩家视角 Match 只出现一次；对手通过同 `game_id`、同格式及另一稳定用户身份关联，只接受可唯一确认的有效对手视角，不以昵称关联比赛。小局通过 `match_id` 和 `duel_index` 关联，不直接展开到主分页。

先完成 Match 计数和分页，再批量取当页 G1、双方快照元数据及可用小局录像，避免 N+1。列表不读取卡片数组、录像 bytea 或账号敏感字段。录像只使用同环境且与当前比赛关联可确认的记录；有多份或歧义时显示未知并隐藏相应操作。对手昵称只有可确认身份时提供跳转。

备选是复用录像列表再按昵称筛选。录像以小局分页，无法正确提供 Match 比分、胜率及总数，不能承担本页历史查询。

### 5. 卡组统计和 G1 次数分别保持完整性

分别按当前环境全时期及所选半年的全部有效玩家视角 Match 左关联 `match_decks` 和环境目录，分组统计 Match 场次、整场胜负。半年模式返回两组独立卡组统计，总战绩模式只返回总卡组统计；历史公开上限与验证状态均不影响两组聚合。缺失快照归独立 `unknown` 行，有快照但未命中具名类型则沿用环境的 `OTHERS`，不得混淆。

G1 只读取本玩家视角、`duel_index=1`、未软删的小局；缺失、歧义或 `is_first=NULL` 均为未知。`firstCount` 与 `secondCount` 分别统计真、假值，`firstRate=firstCount/(firstCount+secondCount)`，分母为零返回 `null`；未知仍保留在 Match 场次和胜负中。应用使用纯领域规则计算胜率及先手率，页面统一格式化百分比并标明 G1 口径。

备选是用全部小局、或用整场场次作先手率分母。前者与用户确认的 G1 口径不符，后者把未知当后手，均不采用。

### 6. 全时期最近二十场倒推、历史积分与查询成本

`matches.points` 是本场变化，不是结算后积分。曲线从总战绩摘要取得该环境的玩家当前总积分，并对全时期有效 Match 按 `date DESC, id DESC` 固定取最多 20 条。领域计算从终点开始，先记录本场结束积分，再减去本场变化得到前一场结束积分；最后反转为时间正序绘图。二十场最多形成二十一个取值，最后一个点始终等于当前总积分；不满二十场仅使用已有记录。统计范围、验证状态与历史页码均不影响曲线；所选半年无记录不隐藏全时期曲线，仅当前环境全时期无有效 Match 时展示空状态。计算曲线不读取第二十一场或累加更早 Match。

当前总积分与全时期最近记录在同一只读一致快照中取得，防止结算事务在两次读取之间提交导致终点与增减错位。半年摘要的积分仍使用半年天梯口径；页面只提供一条全时期最近二十场曲线，不生成所选半年的独立曲线。

历史列表的「结算后总积分」统一从对应玩家当前环境的当前总积分扣除该场之后全时期有效 Match 增减，切换统计范围或翻页不能改变口径或以零为起点。较旧分页可以对当页之后的记录做合计，再倒推当页；这一分页需要的合计不属于固定二十场曲线查询。对手使用自身同环境的当前总积分及全时期后续记录，批量计算而不从本人曲线推算。页面标明列表与曲线均采用全时期总积分口径，最近记录与曲线的同场结算后积分保持一致。

下载复用 `/api/ladder/:format/matches/:matchId/deck` 和 `/api/replays/:format/:replayId`，只返回相关 URL 及完整性状态；本页验证不改变这些既有公开接口。历史 Side 缺失标为 partial，没有可信卡组则隐藏下载按钮。

先复用现有 Match 查询索引、有界最近二十场读取及分页所需合计，不增加统计表、缓存或自动迁移。通过隔离 PostgreSQL 测试验证统一终点、统计范围不影响历史与曲线、半年零战绩仍展示全时期记录、同一快照及有界分页；如未来查询计划证明存在瓶颈，再作为独立有证据的索引优化。

备选是为曲线正序累计全部历史，或为历史和曲线增加半年筛选。前者需要读取更早 Match，后者与用户确认的全时期近期记录口径不符，均不采用。卡组、对手与录像继续批量查询。

## Risks / Trade-offs

- [历史卡组或 G1 先后手未回填] → 保留未知行和未知状态；先手率只用已知记录，不为本页推算或触发回填。
- [公开录像和 YDK 已能读取较早比赛] → 明确本次保护的是新增完整详情历史，不修改既有公开契约，不将二十条限制描述成全站隐私保证。
- [每次分页都校验密码会产生 bcrypt 成本] → 复用公共限流及新增失败预算，保持 stateless 的最小实现；不增加新的账号会话。
- [无 Redis 的多实例失败计数仅在单实例生效] → 默认使用可用 Redis 共享预算；无 Redis 的回退仍提供单实例限制，计数不作为业务持久化状态。
- [原有汇总与比赛明细存在差异] → 曲线明确定义为当前总积分扣除全时期最近二十场增减的倒推趋势，保持终点与总摘要一致，不承诺还原当时的积分快照，不在读取时修补统计或修改历史数据。
- [凭据经网络提交] → 发布环境使用已有 HTTPS 入口，页面不加载外部脚本且不持久化密码；本变更不新增证书或部署流程。

## Migration Plan

1. 实现前确认 `add-replay-deck-access` 对应的类型、快照和小局先后手迁移已在目标环境应用；不要求所有历史完成回填。
2. 在隔离环境运行单元、查询及页面测试，执行 lint、完整 test、资源检查和 build，再完成双环境 HTTP 冒烟。
3. 页面、接口和昵称入口随应用同一版本发布；本变更无新增业务表或资源锁变化。目标环境采用现有发布流程，发布授权另行取得。
4. 回滚应用版本即可移除新增入口及 API，不修改比赛事实、账号、卡组快照或固定资源。
