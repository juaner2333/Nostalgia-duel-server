## Purpose

为已验证的各环境排位初始卡组提供可重复、可追溯的类型判定，使录像展示和筛选读取同一个结果，并使规则更新不会静默改写历史比赛的含义。

## ADDED Requirements

### Requirement: 按环境提供卡组类型目录

`deck_types` 必须（MUST）以 `(format_id, code)` 唯一标识类型，并在同一环境内唯一确定展示顺序。系统必须（MUST）为 1109 提供下表所列的 25 个具名类型及 `OTHERS`（其他），为当前没有具名规则的 1103 提供 `OTHERS`；新增已启用环境但尚无分类规则时，必须（MUST）先提供该环境的 `OTHERS`。`D01` 至 `D25` 是 1109 的固定展示顺序与对外代码，发布后不得（MUST NOT）在 1109 内重排或复用；不同环境可以使用相同代码。`OTHERS` 表示可信卡组已分类但未命中该环境的具名类型。缺少可信卡组快照的“未知”不是（MUST NOT）`OTHERS`，也不作为一个卡组类型代码。`deck_types` 只保存目录元数据，不保存卡片清单或判断条件；实际卡片保存在 `match_decks`，规则由应用代码按环境选择。

#### Scenario: 返回环境内的类型目录

- **WHEN** 1109 或 1103 录像页面请求可筛选的卡组类型
- **THEN** 系统只返回请求环境的目录：1109 按固定顺序返回 D01 至 D25 与 OTHERS，1103 返回 OTHERS；两者都不返回“未知”的伪代码

#### Scenario: 未命中与缺失快照

- **WHEN** 一副可信卡组未命中具名规则，而另一场比赛根本没有可信快照
- **THEN** 前者分类为 OTHERS，后者保持未知，二者在列表和筛选中可区分

### Requirement: 以初始 Main 按固定规则分类

分类器必须（MUST）按 `matches.format_id` 路由，只用 G1 前初始 Main 的卡片判定类型；Extra 和 Side 不参与类型判定。1109 判定前必须（MUST）按随应用发布的固定 1109 卡片数据库中 `datas.alias` 的别名链归一卡片 ID，并对同一原卡 ID 的张数合并计数。1109 分类行为必须（MUST）与分析仓库 `Nostalgia-duel-server-analysis/deck_analysis.py` 在提交 `c9ba01c` 的 `classify_deck` 有序谓词、阈值、卡片集合及首个命中优先级一致；展示顺序不得（MUST NOT）替代规则判定顺序。1103 及其他已启用但没有具名规则的环境，对可信初始卡组必须（MUST）返回该环境的 OTHERS。某环境有具名规则但未命中全部规则时也必须（MUST）返回该环境的 OTHERS；不得（MUST NOT）跨环境套用 1109 规则。

#### Scenario: 异画码归一

- **WHEN** 初始 Main 中含有在固定 1109 CDB 中指向同一原卡的异画码
- **THEN** 分类时合并这些卡的投入张数，导出用快照仍保留各张原始卡片 ID

#### Scenario: 同时命中多条规则

- **WHEN** 一副初始 Main 同时满足两个或更多具名类型规则
- **THEN** 系统按基线规则的声明顺序返回第一条命中的类型，不按 D01 至 D25 展示顺序或命中卡数量重新排序

#### Scenario: 未命中类型

- **WHEN** 一副可信的初始 Main 未满足任一具名规则
- **THEN** 系统记录 OTHERS，页面将其显示为“其他”并允许按 OTHERS 筛选

#### Scenario: 按环境路由与兜底

- **WHEN** 同一副可信 Main 分别属于 1109 与 1103 排位 Match
- **THEN** 1109 使用其固定规则；1103 归为自身目录的 OTHERS，不读取或复用 1109 的规则与类型行

#### Scenario: 固定样本对照

- **WHEN** 用已人工核对的固定 1109 卡组样本运行分类
- **THEN** 25 类的可达样本、边界条件、别名与规则冲突样本均得到与基线规则相同的结果；固定卡池下不可达的类别仍保留其代码

### Requirement: 分类结果附带不可混用的规则版本

每份可信快照必须（MUST）记录环境、卡组类型代码及分类规则版本。版本必须（MUST）标识环境、类别代码映射、谓词顺序、卡片集合、阈值和别名归一策略；没有具名规则的环境也必须（MUST）有明确的兜底版本。任何改变这些行为的发布都必须（MUST）提升对应环境的版本，已有快照不得（MUST NOT）因新规则上线而被静默重新解释。在线采集与历史回填必须（MUST）对同环境、相同卡组使用同一版本的分类行为。

#### Scenario: 在线与回填结果一致

- **WHEN** 同一环境中的同一份 G1 初始 Main 分别由在线结算和历史回填按相同分类版本处理
- **THEN** 两条路径记录相同的类型代码与规则版本

#### Scenario: 规则升级

- **WHEN** 新版本改变任一分类规则、类别映射或别名归一策略
- **THEN** 新快照标识新版本，旧快照继续保留旧版本结果，直到经过明确的重分类过程

### Requirement: 分类不依赖运行时外部仓库

生产分类必须（MUST）只使用本应用发布的对应环境固定资源与代码规则。分析仓库仅作为 1109 具名规则的行为基线，不得（MUST NOT）成为服务运行时文件、Python 解释器或生产数据库连接依赖；数据库不得（MUST NOT）存储或解释可执行分类条件。

#### Scenario: 分析仓库不存在

- **WHEN** 部署环境不包含 `Nostalgia-duel-server-analysis` 仓库
- **THEN** 1109 在线卡组分类以及各环境录像类型展示与类型筛选仍可正常工作
