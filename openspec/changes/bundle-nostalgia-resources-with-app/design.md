## Context

变更动机参见 `proposal.md`，行为契约参见 `specs/application-bundled-resources/spec.md` 与 `specs/ygopro-only-server/spec.md`。

现有 `clone_repositories.sh`、`setup_resources.sh`、manifest assembly、`resources/releases/<id>` 和 `resources/current` 软链接继承自 master 的运行时资源热更新设计。master 同时具有后台 updater、CDB 定时重载和 LFList 定时重载；当前分支已经移除这些应用内重载入口，唯一资源 source 也已变为仓库内 `nostalgia-resources/`。因此现有脚本每次只是把已提交资源复制为第二份目录，再通过软链接供应用读取。

固定资源已经具备直接运行所需布局，且 `lock.json` 记录基础数据库、双环境卡池、LFList 与脚本摘要。项目已有生成和校验 lock 的 TypeScript 能力，无需新增依赖。

## Goals / Non-Goals

**Goals:**

- 让应用代码与固定怀旧资源只有一个版本号、一个发布动作和一个回滚边界。
- 让干净检出的本地源码无需资源准备步骤即可启动。
- 在删除通用资源管线后继续保持或加强完整性、YGOPro-only 和固定卡池门禁。
- 删除已经没有运行时消费者的 source、assembly、release、软链接、GC 与刷新概念。
- 保持 1103/1109 卡池、规则、脚本查找顺序、资源版本 API 和决斗行为不变。

**Non-Goals:**

- 不提供独立资源发布、运行时热更新、远程 Git/HTTP source 或私有资源覆盖。
- 不改变 1103/1109 的 CDB、白名单、LFList 或 Lua 内容。
- 不增加第三种怀旧环境，也不设计未来的动态赛制注册机制。
- 不修改 YGOPro 线协议、房间状态机、录像、匹配或 WindBot 行为。
- 不引入新的资源包管理器、对象存储或第三方完整性工具。

## Decisions

### 1. 运行时直接使用唯一固定资源根

默认 `RESOURCES_DIR` 改为 `./nostalgia-resources`，开发环境、编译产物和容器均使用相同目录布局。运行时按固定约定解析：

```text
nostalgia-resources/
├── lock.json
└── ygopro/
    ├── base/{cards.cdb,script/}
    └── formats/{1103,1109}/{lflist.conf,script/}
```

删除 `MANIFEST_PATH` 和运行时 manifest 解析。基础设施从固定资源根与领域层注册的 `1103`、`1109` 标识派生路径，未知环境继续在现有准入边界被拒绝。

没有选择保留精简 manifest，因为当前允许的环境已经由领域注册表确定，第二份路径配置只会制造漂移。没有选择把 `resources/current` 直接改成普通目录，因为它仍会保留一个没有独立版本含义的复制层。

### 2. 完整资源校验在启动、CI 和镜像构建复用同一实现

扩展现有资源校验入口，使其对资源根调用完整 lock 校验，而不只分别检查两份 LFList。校验覆盖 CDB 集合、双环境白名单与限制数量、LFList 摘要、基础与 format 脚本摘要、必需文件以及禁止出现的目录。

应用在打开持久化连接和监听端口之前执行一次同样的完整校验并失败即停，保证 `npm run dev`、编译后运行和容器启动不会绕过门禁。CI 和 Docker 构建显式运行该命令，以便在制品产生前提供更快的失败反馈。

没有只依赖 Git 状态或 Docker COPY，因为本地未提交修改、错误的忽略规则和不完整构建上下文仍可能造成资源漂移。一次性校验会读取约 20 MB 固定资源和脚本目录，接受这项启动成本以换取统一安全边界。

### 3. Docker 镜像直接携带资源

构建阶段在完整性校验通过后，将 `nostalgia-resources/` 原样复制到最终镜像。最终入口直接启动 Node.js 服务，不执行资源获取、组装或发布脚本。Compose 不再传递 manifest 路径，也不挂载独立活动资源目录。

镜像标签或摘要成为应用与资源的联合版本。部署回滚通过恢复上一镜像完成，不再修改资源软链接。资源版本接口继续读取镜像内 `lock.json` 并报告实际加载摘要。

没有选择在镜像构建时生成新的 lock；生成 lock 是维护者对有意资源变更的显式操作，构建只能校验，不能替修改者掩盖未审核漂移。

### 4. 删除遗留通用资源管线而非保留休眠代码

删除资源 clone/setup 库、通用 source/assembly manifest、release/GC 约定和只验证这些行为的 Bats 用例。若 `scripts/entrypoint.sh` 只剩执行 Node.js，则由容器 `CMD` 直接表达；其他仍有独立消费者的运维脚本按引用审计保留。

README、`.env.example`、AGENTS 和部署说明统一为直接资源路径。测试改为验证干净固定布局、完整 lock 失败语义、无外部 source、镜像内容和版本接口。

没有选择为了潜在未来热更新保留这些抽象。若业务目标变化，热更新需要完整的资源快照、房间版本绑定和原子内存切换，不能由当前两个 shell 脚本安全恢复。

### 5. 发布和回滚只接受整体版本

资源修改流程固定为：编辑受控文件、显式生成新 lock、评审资源与 lock 差异、通过完整检查、构建新应用制品。生产发布先保留上一镜像，部署新镜像并完成 1103/1109 冒烟测试后，再按既有镜像保留策略清理旧制品。

任何资源故障均回滚完整镜像。系统不支持把旧应用与新资源或新应用与旧资源拼接，也不维护兼容矩阵。

## Risks / Trade-offs

- [完整 lock 校验增加启动时间] → 只在进程启动时执行一次，并复用现有摘要算法；记录实际耗时，若明显影响启动再在不削弱 CI/构建门禁的前提下优化 I/O。
- [删除 manifest 后路径配置失去通用扩展性] → 这是固定 1103/1109 边界的有意结果；新增环境必须通过独立变更扩展领域注册表、资源布局和 lock。
- [应用与资源强绑定导致微小脚本修正也要发布镜像] → 这是保证裁定可复现的核心权衡；项目由单一维护者运营且资源更新频率低，额外发布成本可接受。
- [删除旧管线时误删仍被 Docker 或测试使用的脚本] → 按全仓库引用逐项删除，并从干净检出构建最终镜像验证不存在对忽略文件的依赖。
- [旧部署残留 `resources/releases` 占用磁盘] → 新镜像验证成功后再按明确路径清理；不在应用启动时自动执行破坏性 GC。
- [历史文档继续提示执行资源脚本] → 将 README、AGENTS、环境示例和运维说明纳入同一变更的验收检查。

## Migration Plan

1. 为直接固定布局、完整 lock 校验失败、无资源准备启动及版本接口增加回归测试。
2. 让运行时从固定资源根派生 base 与 1103/1109 路径，并在监听端口前执行完整校验。
3. 将 npm、环境示例、Docker 和 Compose 切换到 `nostalgia-resources/`，从干净检出构建并启动候选镜像。
4. 删除 manifest/source/assembly、clone/setup/release/GC 代码及其专用测试，完成全仓库引用审计。
5. 更新开发和部署文档，运行完整 lint、测试、构建、资源校验及镜像内容检查。
6. 保留当前生产镜像，部署新整体制品并分别完成 1103、1109 建房、卡组校验、真实 WASM 决斗和资源版本接口冒烟测试。
7. 验证稳定后再删除宿主机或旧容器中明确识别的 `repositories` 与 `resources/releases` 遗留目录。

回滚时恢复上一应用镜像及其环境配置；不得单独恢复或挂载旧 `resources/current`。在新镜像验证完成前不执行遗留目录清理。
