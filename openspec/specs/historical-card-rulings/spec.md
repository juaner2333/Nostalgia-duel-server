# historical-card-rulings Specification

## Purpose
定义 1103 与 1109 怀旧环境对已确认旧卡采用 2011 OCG 效果处理的可验证行为，使后续文本勘误和现代脚本更新不会改变固定怀旧对局的发动次数、对象、时点或表示形式。

## Requirements

### Requirement: 双环境提供固定的 2011 裁定覆盖集合

系统必须（SHALL）在 1103 与 1109 各自的 format 脚本目录中提供固定的 2011 裁定覆盖集合。该集合等于上游 `purerosefallen/specials` 仓库 `706` 目录（固定提交 `f993d739344f1914bcf8c54e90d638eb1fb45d45`）中属于对应环境白名单的全部卡片脚本（1103 为 374 张、1109 为 375 张），加上上游没有的两张本项目覆盖 `80168720` 与 `96782886`；因此 1103 目录必须（SHALL）包含 376 个卡片脚本、1109 目录必须（SHALL）包含 377 个卡片脚本。与既有覆盖重叠的 10 张必须（SHALL）采用上游版本。同一卡片 ID 在两个环境的脚本必须（SHALL）逐字节一致。系统不得（SHALL NOT）把不属于对应环境白名单的上游脚本纳入该环境，也不得（SHALL NOT）读取另一环境的脚本目录。

#### Scenario: 1103 与 1109 请求已覆盖卡片

- **WHEN** 1103 或 1109 对局请求集合内任一卡片的 Lua 脚本
- **THEN** 系统加载当前房间 format 内的 2011 裁定脚本而不是现代 base 版本

#### Scenario: 集合内脚本双环境逐字节一致

- **WHEN** 比较两个 format 目录中同一卡片 ID 的脚本文件
- **THEN** 两个文件内容完全一致（包括上游引入的脚本与本项目保留的 `80168720`、`96782886`）

#### Scenario: 两个环境含有相同卡片

- **WHEN** 同一覆盖卡片分别在 1103 与 1109 对局中进入可触发其效果的相同局面
- **THEN** 两个对局执行等价的 2011 OCG 效果处理

#### Scenario: 当前环境缺少覆盖脚本

- **WHEN** 被请求的卡片脚本不在当前 format 目录但存在于另一 format 目录
- **THEN** 系统不得读取另一 format 的脚本，并继续遵循既有的当前 format 到 base 的查找边界

#### Scenario: 白名单外的上游脚本不进入运行时

- **WHEN** 上游 706 目录中的卡片不属于对应环境的白名单（如 `27847700` 等 6 张不属于任何环境白名单，`67750322` 不属于 1103 白名单）
- **THEN** 该脚本不得出现在对应环境的 format 目录中，也不得被对局加载

### Requirement: 每局决斗预加载全局旧裁定补丁

系统必须（SHALL）在 1103 与 1109 的每局决斗中、加载任何卡片脚本之前，通过引擎预加载机制执行当前 format 脚本目录中的 `special.lua`；两个环境中的该文件必须（SHALL）逐字节一致。补丁必须（SHALL）恢复以下 2011 全局裁定：反转召唤被无效的怪兽不视为从场上送去墓地；被无效反转召唤的怪兽不被标记完成召唤手续（保持可苏生）；离场重定向类效果在反转召唤被无效时不触发。补丁必须（SHALL）向卡脚本提供 `Card.GetFlipEffect` 与 `Auxiliary.dserodcon`。`special.lua` 必须作为固定资源的一部分接受资源锁校验。

#### Scenario: 反转召唤被无效不算场上送墓

- **WHEN** 一只怪兽的翻转召唤被「召唤无效」类效果无效，且存在「从场上送去墓地时」触发的效果
- **THEN** 该触发效果不发动，被无效的怪兽按 2011 裁定不视为从场上送去墓地

#### Scenario: 被无效的反转召唤怪兽保持可苏生

- **WHEN** 一只怪兽的翻转召唤被「召唤无效」类效果无效
- **THEN** 该怪兽之后仍可通过苏生效果从墓地特殊召唤

#### Scenario: 依赖补丁 API 的卡脚本正常运行

- **WHEN** 集合内的卡脚本调用 `Card.GetFlipEffect` 或 `Auxiliary.dserodcon`
- **THEN** 脚本在补丁预加载后正常执行，不因缺少补丁提供的 API 而报错

#### Scenario: 补丁缺失或漂移时资源完整性检查失败

- **WHEN** 任一环境的 format 脚本目录缺少 `special.lua`，或其内容与资源锁记录不一致
- **THEN** 固定资源完整性检查失败

### Requirement: 全量覆盖脚本通过真实引擎加载验证

纳入 format 目录的全部脚本必须（SHALL）在应用使用的 ocgcore WASM 引擎中成功加载，不得（SHALL NOT）因语法错误、未定义常量或不支持的 API 写法导致对局失败。

#### Scenario: 全量脚本在真实引擎中加载

- **WHEN** 对两个环境 format 目录中的全部脚本在真实 ocgcore WASM 中执行加载验证
- **THEN** 每个脚本均成功加载，不产生脚本错误

#### Scenario: 使用新导入脚本的完整对局

- **WHEN** 双环境冒烟对局或回归场景使用新导入的脚本进行完整决斗
- **THEN** 决斗正常推进至结束，不出现脚本错误或引擎异常

### Requirement: 历史裁定资源可复现且不改变卡池

历史裁定覆盖必须（SHALL）随应用固定资源锁定和发布，`special.lua` 与全部 format 脚本一并纳入锁校验。增加覆盖不得（SHALL NOT）改变基础数据库、1103/1109 白名单、禁限数量、房间规则或 Master Rule 2 配置。

#### Scenario: 校验历史裁定资源

- **WHEN** 执行固定资源完整性检查
- **THEN** 两个 format 的脚本文件集合（含 `special.lua`）及内容摘要与资源锁一致，全部纳入的脚本卡片均存在于固定基础数据库和对应 format 白名单中

#### Scenario: 未更新资源锁而修改脚本

- **WHEN** 任一 format 脚本或 `special.lua` 发生增删或内容变化但未重新生成资源锁
- **THEN** 固定资源完整性检查失败

#### Scenario: 比较变更前后的卡池与禁限数量

- **WHEN** 完成脚本导入并重新生成资源锁
- **THEN** 基础卡片 ID 摘要、1103/1109 卡池数量与两份 LFList 内容保持不变，仅格式脚本和资源锁对应摘要发生变化

### Requirement: 历史裁定修复记录可追溯

仓库必须（SHALL）提供 `docs/historical-card-rulings.md`，记录已修复集合的上游来源（仓库与固定提交）、与既有覆盖的冲突处理（被上游版本替换的卡片、本项目保留的卡片）、排除的卡片及原因、后续可能修复的候选脚本和旧裁定来源。已修复记录必须（SHALL）与实际双环境覆盖一致；候选记录不得（SHALL NOT）被表述为已实现或自动进入运行时脚本集合。

#### Scenario: 记录上游来源与冲突处理

- **WHEN** 本次脚本导入完成
- **THEN** 文档记录上游仓库地址与固定提交、被上游版本替换的 10 张重叠卡片、保留的 `80168720` 与 `96782886`、排除的 6 张白名单外卡片及其原因

#### Scenario: 记录尚待考证或待实现的脚本

- **WHEN** 调查发现可能需要旧裁定覆盖但尚未纳入本次实现的卡片
- **THEN** 文档在独立候选章节记录其 ID、卡名、疑似差异、适用环境、证据状态和待决问题，并明确其尚未修复

#### Scenario: 记录旧裁定来源

- **WHEN** 文档引用上游旧裁定脚本或历史资料
- **THEN** 来源包含可追溯的仓库、固定提交或文件路径，并在存在虚拟卡片 ID 时记录其与正式卡片 ID 的映射
